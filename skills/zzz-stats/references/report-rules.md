# 抽卡报表规则（规范）

这个文件是**报表口径与呈现的规范**，回答两个问题：**为什么这样算**、**为什么这样画**。
它不随实现变化——代码可以重写、模板可以替换，这里定义的规则是要长期守住的。

## 谁该读这个文件

| 读者 | 用法 |
|---|---|
| **用户 / Agent 日常出报表** | **不用读这个文件**。直接 `node skills/zzz-stats/scripts/build-report.mjs`，模板已经实现全部规则 |
| **开发 / 修改这个 skill** | **必须读**。改口径、改配色、改版式前先看这里，改完回来同步 |
| **接手维护的人** | 先读这里，再看 `scripts/build-report.mjs` 与 `assets/report/` 的实现 |

**规则与实现的分工：**

| 层 | 位置 | 角色 |
|---|---|---|
| 规则（本文件） | `references/report-rules.md` | 规范。定义口径、配色语义、版式要求、踩过的坑 |
| 配置 | `config/report.json` | 可调参数：称号分档、标签阈值、配色值、文案、频道定义 |
| 实现 | `scripts/build-report.mjs` + `assets/report/` | 默认模板。把规则落成可运行代码 |

**优先用模板，不要重新发明**：`scripts/build-report.mjs` 已经实现了下面的全部规则。
只有在模板确实不适用、或你要做定制版式时，才需要按本文件手写实现。

## 0. 怎么出报表

```bash
node skills/zzz-stats/scripts/build-report.mjs          # output/<账号名>/data/ → output/<账号名>/report.html
```

产物：单文件 `output/<账号名>/report.html`，内联数据、ECharts 与用到的图标（base64），可单独发送。
产物路径规则是「数据集目录的上一级 + 固定名 `report.html`」，所以报表和数据同处一个账号目录，
拿走那一个目录就能部署。显式 `--data fixtures/xxx` 时不会往 `fixtures/` 里写，
改取该数据集 `meta.json` 的昵称落到 `output/<昵称>/report.html`。
ECharts 5.6.0 已 vendored 在 `assets/vendor/echarts.min.js`（校验见 §7），报表不联网、不用 CDN。

## 1. 口径

- **UP 轮**：从上一个 UP 结束后开始。`off` = 期间所有非 UP 金的抽数，`up` = UP 金自己的抽数，`total = off + up`。
- **十连副金并回本轮**：同一发十连里排在 UP **之后**的非 UP 金（`record_time` 同秒且 `sort` 差 ≤ 9），把它的 `count` 并入这一轮的总抽，本轮仍算**直出**。不留给下一个 UP——否则下一位会被误判成「先歪」。
- **保底获得（guar）**：上一轮末尾带出了十连副金，说明 50/50 已经歪过，这一发是大保底。它**不计入 50/50 胜场**，并且**打断连 UP**。
- **指标**（每金 / 每 UP 一律用「官方总抽 − 当前垫抽」）：
  - 每 UP 均 = (角色池总抽 − 角色池垫抽) / UP 轮数
  - 不歪率 = 胜场 / UP 轮数（胜场 = 直出且非保底获得）
  - 平均每金 = (该频道总抽 − 该频道垫抽) / S 数
  - **为什么扣垫抽**：`type_stats[].total_count` 含「已经抽掉、但还没出 S」的垫抽。
    把它摊进每个金，等于把一个尚未结算的成本算进历史均值。官方自己的 `avr_up_count`
    就是扣掉垫抽的：常驻 650/9 = 72.2，官方 65.8 = (650−58)/9；独家重映 90/1 = 90，官方 76 = (90−14)/1。
    示例账号的角色池垫抽恰好是 0，所以旧口径没露馅——换个号就会系统性偏非，**称号也会跟着偏**。
  - 报表构建时会拿扣垫抽后的每金和官方 `avr_up_count` 交叉核对，差超 0.1 就告警。
- **欧判定**：`total ≤ 该账号的每 UP 均` 即算欧（歪了但更省也算）。**不要写死 87.9**，那是示例账号的值。
- **极欧**：`total ≤ 40`（`config.report.json` 的 `numbers.extremePulls`）。

### 1.1 完整性校验

```
sum(cur_records[].count) + type_stats[].next_s_cur_times == type_stats[].total_count
```

6/6 频道实测成立。它校验的是**抽数**，比「金数对得上」更强。
另：`index.total_gacha_count` 与 `total_s_count` **都不含邦布**（实测 3714 / 62，六频道相加 5375 / 96）。
**邦布抽卡用的是邦布币，和调频券不是同一种货币**，所以跨频道的「总抽卡数 / 平均每金 / S 级总数」一律扣掉邦布，只统计同一货币的频道（`config.report.json` 里 `channels[].countsTowardTotals`）。邦布自己的每金成本在 KPI「每邦布」里单独给。

## 2. 首屏

- **标题行**：`昵称 · UID 胶囊 · 大标题 · 隐私开关（眼睛）`，右侧留白处放 **GitHub 仓库链接**，一行不换行。
  - **显示的是安装命令 `npx skills add atian25/zzz-stats`，不是裸 URL**，点击仍打开仓库。
    看到报表的人最可能想做的是装上它，一条能直接粘的命令比还要再翻 README 的地址有用。
    地址与文案在 `config/report.json` 的 `copy.repo`。
  - 文字前带 **GitHub 图标**（内联 SVG，`currentColor` 描边，13px），整行用 `inline-flex` 垂直居中。
  - 样式要低调：等宽小字、灰色，hover 时图标与文字一起变主题金色；`target="_blank" rel="noopener"`。
  - 只替换文字节点、保留图标（`#repo-text`），不要用 `textContent` 整段覆盖，否则 SVG 会被清掉。
  顺序是「先是谁，再是账号标识，最后是评价」——称号放最后，因为它是对这个人的结论，不是身份信息。
- **大标题**：按每 UP 均查 `config.report.json` 的 `titles.tiers`（10 档，见 §4）。**按公式算出再写**，不要写死。
- **次行四项**：`N 抽 总抽卡数 / N S 级代理人 / N UP 代理人 / N UP 音擎`，
  行尾灰色等宽小字 `国服 · 采集 YYYY-MM-DD HH:MM`。
  - **不要放版本区间**：版本在横轴上已经按柱标注了，行尾再写一遍是冗余。
  - **不要放 region**（`prod_gf_cn` 这类）：对读者没有意义，排查问题时看 `data/meta.json`。
  - **时间必须带年份**：跨年看报表时 `MM-DD` 会有歧义。
  - **前两项 = 全账号汇总**，口径是「除邦布外全部五个频道」，
    实测 `2372(UP) + 650(常驻) + 590(音擎) + 90(独家重映) + 12(音擎回响) = 3714`，
    与官方 `total_gacha_count` / `total_s_count` 完全一致（3714 / 62）。
  - **后两项 = UP 数**，取自官方 `type_stats[].up_count`（实测代理人 27、音擎 8）。
    **UP 写「UP 代理人 / UP 音擎」即可，不要再加「S 级」**——UP 角色的稀有度恒为 S，写了是废话。
  - **注意 41 ≠ 27**：41 是「独家」频道的全部 S（27 UP + 13 歪出 + 1 副金），62 是全账号全部 S。
    不要把 41 当 UP 数。
  - **用「代理人」而不是「角色」**：游戏内角色池抽出来的就是代理人，术语要跟游戏一致。
  - **不放「UP 池抽卡数」**：该数字在下方 KPI「每 UP 角色」的语境里已经隐含，首屏不必再占一格。
  - **界面上不要堆括注**（`不含邦布` / `含歪出` 之类）：口径写在本文件里，界面只给干净的四项。
  - **不要写「平均每金」这种跨频道混算值**：`3714 ÷ 62 = 59.9` 把不同频道的抽数合在一起除以总金数，
    等于假定它们在同一个计价体系，实际期望完全不同。各频道真实成本看下面的 KPI。
- **KPI 固定 5 格一行**（窄屏也不折行）：`角色池不歪 / 每 UP 角色 / 每 UP 音擎 / 常驻每金 / 每邦布`。
  这 5 个数全部按「扣垫抽」口径算（见 §1），不要退回含垫抽的总抽 ÷ 金数。
- **隐私开关**：称号右侧的眼睛按钮（UID 胶囊只负责显示），**三态循环**（默认全显示）：① 全显示 → ② 仅打码 UID（`UID 116***92`）→ ③ 全打码（昵称只留首字 + UID 打码）→ 回到 ①。图标用内联 SVG 三态。
  **对外截图必须先点到全打码（从默认点 2 下）。**
  - **这条不是提醒，是硬约束。** 已经踩过一次：README 的预览图连着两版把真名和 UID
    截进了公开仓库，事后才发现。截图脚本里必须先
    `eye.click(); eye.click();`，再断言 `#eye` 的 `data-state === '2'` 与
    `#nick` 含 `*`，断言不过就**中止截图**——宁可没有图，也不要一张带真名的图。
  - 打码版一旦提交、推送就收不回来了：`git show <旧commit>:docs/preview.png` 永远取得到。
    所以这一步只能在截图前做对，事后补救是补不回来的。
- `document.title` 也要跟着三态变，否则标签页会泄露昵称、或与页面状态不一致。
- **验证隐私开关时不要用已打码的昵称做数据**：`maskName('天*')` 仍返回 `天*`，
  看起来像「点了没反应」。测试数据里要放完整昵称，才能验证状态 2 真的把名字盖掉。

#### 2.1 `--preview` 的隐私分流：模拟数据集不打码，真实数据一个字都不许松

`--preview` 出的是 README 头图（`docs/preview.png`），任何人都看得到。它的隐私行为
**按数据集来源分两条路**，判据只有一个——产物里的 `report.meta.synthetic`：

| 产物里的 `meta.synthetic` | 截图前 | 截图前的断言 | 结果 |
|---|---|---|---|
| **严格布尔 `true`** | 不点眼睛，保持状态 0 | 昵称/UID **不含** `*`；且都不能为空 | `绳匠A` / `UID 10000001` 原样进图 |
| **其它一切**（`false` / `"true"` 字符串 / `1` / 缺失 / 产物读不出 report） | 强制点到 **2** | 原有那条：`eye==='2'` 且昵称、UID 都**含** `*` | 遮成 `绳*` / `UID 100***01` |

- **改之前**：`const EFFECTIVE_PRIVACY = PREVIEW ? 2 : PRIVACY` —— 无条件强制 2，断言无条件要求含 `*`。
  连 `fixtures/baseline`（`绳匠A` / `10000001`，本来就是编的）也被遮成「绳*****」。
- **改之后**：先读产物里的标记再决定。`synthetic: true` 的数据集不遮；其余维持原样。
- **为什么**：模拟名字遮了不保护任何人，只是让预览图难看、并且掩盖真实排版
  （用户原话：「github 截图没更新，既然是模拟名字的话，就不用打星号了」）。
- **fail-safe 规则：没有标记一律当真实数据。**
  不猜、不按 UID 长度或昵称形状推断——「这个号看起来像假的」这种判断每个都可能猜错一次，
  猜错的代价是真名进公开仓库；而「忘了写标记」的代价只是图难看一点。
  所以 `"synthetic": "true"`（字符串）也按真实处理：手写 JSON 时最容易犯的正是这个错。
- **断言不许拆，只许反过来写**。两条分支都断言，方向相反：
  真实数据必须「已遮住」，模拟数据必须「没被遮」。
  把模拟分支写成「不管」的话，一次 JS 崩溃导致昵称空白、或把 synthetic 判错，
  就会静悄悄截出一张坏图；反着断言，两种事故都当场中止、不写文件。

实现分两处：判定逻辑在 `scripts/preview-privacy.mjs`（纯函数，`extractReport()` /
`previewPrivacyPolicy()` / `checkPreviewGuard()`），接线在 `scripts/screenshot.mjs`。
回归用例：`node skills/zzz-stats/scripts/test-preview-privacy.mjs`（不需要浏览器）。
基线是 **53 项**；本机因为 `output/` 下同时有 `绳匠A` 与 `绳匠B` 两个数据集目录，
第 5 节对每个目录各跑一条，实际是 **55 项**——数字随 `output/` 里的账号目录数变化，
不是回归。

**数据集怎么标**：`fixtures/<数据集>/meta.json` 里写 `"synthetic": true`。
`scripts/build-report.mjs` 用 `meta.synthetic === true` 透传到 `report.meta.synthetic`，
前端不读这个字段（不进任何渲染路径），只有 `--preview` 消费它。

## 3. 主图（`抽卡总览`）

### 3.0 配色语义（值在 `config.report.json` → `colors`）

颜色不是装饰，每一个都对应一个判定，换色等于换语义：

| 含义 | 色值 |
|---|---|
| 极欧 ≤ 40 抽（本发上段） | 蓝 `#3F7BFF` |
| 极欧周期的歪段 | 深蓝 `#1B3C78` |
| 欧 > 40 抽（本发上段） | 深绿 `#2E8F45` |
| 欧周期的歪段 | 深绿 `#1B5E2A` |
| 非酋本发上段（超均值） | 亮红 `#FF5F6D` |
| 非酋歪段 | 深红 `#A81E28` |
| 累计不歪率折线（非酋 <35%） | 红 `#FF8A94` |
| 累计不歪率折线（薛定谔 35~50%） | 绿 `#5FD98A` |
| 累计不歪率折线（大欧 ≥50%） | 蓝 `#7FB4FF` |
| 折线描边（三档共用） | 深色 `#0d0d10` |
| 十连多金圆点 | 青 `#7BE0FF` |
| 版本分隔虚线 | 灰 `#3A3A42` |

**堆叠柱的读法**：下段 = 歪掉的抽数，上段 = UP 本身。**柱体颜色表达运气（欧/非），不表达 50/50 输赢**——
「歪」只在第二屏用红章标出。这两件事不要混在一根柱子上表达。

### 3.1 版式

- 面板标题 `抽卡总览`（15px/700），右侧灰字 `N 个 UP · N 抽`。
  - **主图支持切频段**：标题右侧是频段 tab（独家 / 音擎 …），与第二屏的 `.detail-tab` 同一套读法（金色下划线＝选中）。
    只渲染**有 50/50 且真的折出了 UP 轮**的频道；常驻/邦布没有 UP 概念，独家重映/音擎回响常为 0 轮，都不给 tab（点进去全空的 tab 比没有更差）。
    只有一个频道可画时整条 tab 不渲染。
  - **为什么音擎要切数据集而不是加成柱子**：音擎保底 80 抽、每 UP 抽数也自成一套，并进角色池的柱子会让两边的「超出均值」判定都不成立。
  - **版本过滤**（`1.x` / `2.x` / `3.x`，多选）：只列该账号真实出现过的档位，不写死。
    全部取消＝回到全显示（不是画空图）。切换频段时**保留**过滤选择——两个频道共用同一套版本号。
    形态是「漏斗图标 + 带勾选态的标签」：外层 chip 无框无底，内层是 12×12 的细框勾选框；
    选中是「灰框 + 勾」，未选中是「灰框 + 短横」。
    **勾选框那个方框不能删**——它是「这里可以勾」的唯一视觉暗示，删了整排就退化成一行说明文字。
    **选中态不能用金色**：`--accent`（金 `#F5C04A`）在这份报表里代表「欧气/好运」（`tag[data-tone="positive"]` 就用它），
    过滤器勾上 ≠ 好运，用金色是错误暗示。金色留给 tab 选中态（那是「你在看哪个」，与运气无关）。
    **区分也不能只靠颜色差**（早先就是实心金色 chip vs 灰描边，压成灰度后分不出来）；
    勾 vs 短横是形状差异，压色、缩小都还认得出来。
    icon 必须是**内联 SVG**，不能引外部图标库——产物要能单文件离线打开。
    窄屏（≤720px）过滤条换行独占一行并允许横向滚动，否则会被面板右边裁掉、点不到。
  - **不歪率折线始终按「全局累计」算，版本过滤只缩柱子、绝不重算折线。**
    这是用户定死的口径，**不要改**。原因：过滤是为了「只看 2.x 那几根柱子」，
    如果折线也跟着重新累计，同一根柱子在不同过滤组合下会落在不同的折线高度上，
    读者会以为数据自相矛盾；折线表达的是「这个号一路走来的整体水平」，不该随筛选变化。
  - 不过滤时右侧写官方口径的该频道总抽数（`chart.pulls`），**不要用柱子求和**——两者差的是垫抽（实测 6320 官方 vs 6318 柱和）。
    过滤生效后改写 `{shown} / {upCount} 个 UP · {pulls} 抽`，其中 pulls 是可见柱之和，否则数字和图对不上。
- **堆叠柱**：下段 = `off`（歪掉的抽数），上段 = `up`（含十连副金）。**柱顶**写本轮总成本；**柱内**各段写各自抽数（段 < 8 抽不写）。
- **柱宽必须同时设百分比和像素上限**：`barWidth: '46%'` 的百分比基数是**类目带宽**，不是画布宽度。
  柱少时类目带宽变大，46% 会撑成巨型色块——实测独家重映只有 1 根柱时宽 **600px**，而 71 根柱时每根只有 96px。
  所以两段柱（`off` / `up`）都要加 `barMaxWidth`，取值走 `config/report.json` 的 `numbers.barMaxWidth`（默认 56），
  改配置就生效，不要在 JS 里另写死数。**两段必须同值**，否则同一根柱的上下段宽度不一致，会错位成阶梯形。
- **不歪率折线按三档分色，红 / 绿 / 蓝与柱体同语义**（`config.numbers.winRateTiers` + `colors.winRate*`）：

  | 不歪率 | 判定 | 折线颜色 | 对应柱体色 |
  |---|---|---|---|
  | `< 35%` | 非酋 | 红 `#FF8A94` | bad 红 `#FF5F6D` |
  | `35% ~ 50%` | 薛定谔（还没定型） | 绿 `#5FD98A` | good 绿 `#2E8F45` |
  | `>= 50%` | 大欧 | 蓝 `#7FB4FF` | extreme 蓝 `#3F7BFF` |

  - **两套颜色是同一套语义的两种亮度，不是两套配色**：
    柱体的红/绿/蓝表达「这一轮差于均值 / 好于均值 / 极欧」，
    折线的红/绿/蓝表达「这个号在此刻的累计水平是非酋 / 还在薛定谔带 / 大欧」。
    都遵循「红<绿<蓝＝从差到好」同一条阶梯，读者不需要学第二套读法。
  - **折线必须用同色相的提亮版，不能直接复用柱体色值**：折线会横穿柱子，
    同色时对比度只有 1.0~1.4（实测红折线过红柱 1.00、绿折线过绿柱 1.00、蓝折线过蓝柱 1.00）——
    压在柱子上等于看不见。提亮后对柱体 1.5~2.3、对底色 7.7~10.9，既认得出是同一档，又压得住。
    色值键是 `colors.winRateUnlucky` / `winRateSchrodinger` / `winRateLucky`（对应 `numbers.winRateTiers` 的三个 key）。

  - **提亮不够，折线还必须加深色描边（halo）**。提亮版压在**同类柱子**上仍然低于 3:1：

    | 折线 | 压在同色柱上 | 判定 |
    |---|---|---|
    | 红 `#FF8A94` | 红柱 `#FF5F6D` | **1.31 : 1** |
    | 绿 `#5FD98A` | 绿柱 `#2E8F45` | **2.30 : 1** |
    | 蓝 `#7FB4FF` | 蓝柱 `#3F7BFF` | **1.80 : 1** |

    三档全部低于 3:1，且是**最该看清的那一段**（自己的累计水平正好落在自己那一档的柱子上）。

    做法：**同一段线画两遍，先粗后细**。粗的那遍用深色 `colors.winRateHalo`（`#0d0d10`，与 tooltip 底色同值），
    细的那遍才是彩色线。彩色线 1.4px、描边 4.6px，两侧各露出 1.6px。
    **1.6px 这个数字不能改小**：取 3px 时每侧只有 0.8px，属亚像素，抗锯齿会把描边和柱色混成一团，
    实测紧邻对比度只有 1.09~1.47，与没加描边（1.31）几乎一样，等于白做。
    圆点同样画两遍（描边圈 r=4.2、彩点 r=2.6），否则线头会从节点两侧露出来。

    实测（基线账号 1440×900 截图像素，按「线的紧邻像素」分类统计）：

    | 折线 | 紧邻描边时 | 描边覆盖率 |
    |---|---|---|
    | 红 | 中位 **5.67 : 1**，最小 2.80 | 78% |
    | 绿 | 中位 **9.13 : 1**，最小 5.66 | 97% |
    | 蓝 | 中位 **6.69 : 1**，最小 3.10 | 91% |

    剩余未覆盖的像素集中在**柱子顶部的抗锯齿边缘**（线恰好压在柱顶那一两行上），描边被柱子的边缘像素吸收。
    这部分无法靠加粗解决，只能靠加宽——但再加宽就会把柱子挖出一条明显的黑沟，得不偿失。

    **为什么不用另外两个方案**：
    - **加半透明底衬**会弄脏柱子：一块 40% 不透明的黑色蒙版压在柱子上，柱子本身的颜色就没法读了，
      而柱子颜色是「歪掉的抽数 / UP 抽数」的语义，不能为折线让路。
    - **换更亮的绿**只解决绿色档，红蓝两档仍然低于 3:1（它们本来就比绿更亮，没有提亮空间）。
      而且三档亮度拉开后，就不是「同一条阶梯」了。
    - 描边色取**实色深色**而不是半透明黑：半透明会吃进柱子的色相，在红柱上偏红、在绿柱上偏绿，
      三档分开后描边本身又变得不一致。

    **描边在深色柱段上会糊，这是已知且可接受的局限**：

    | 描边 `#0d0d10` 压在 | 对比度 |
    |---|---|
    | 红柱浅色上段 `#FF5F6D` | 6.57 : 1 |
    | 绿柱浅色上段 `#2E8F45` | 4.74 : 1 |
    | 蓝柱浅色上段 `#3F7BFF` | 5.07 : 1 |
    | 红柱深色下段 `#A81E28` | **2.66 : 1** |
    | 绿柱深色下段 `#1B5E2A` | **2.48 : 1** |
    | 蓝柱深色下段 `#1B3C78` | **1.82 : 1** |

    深色下段那三行低于 3:1，描边几乎糊进柱子里。**但这一档本来就不需要描边**：
    彩色线压在深色段上本身就有 3.23 / 4.09 / 4.39（红/绿/蓝），全部达标——
    会「看不见」的是浅色上段（1.31~2.30），而那正是描边起作用的地方。
    换句话说，描边的有效区间与需要它的区间正好重合。

    想把深色段也拉开，只能把描边改浅（那会在浅色段失效）或加半透明底衬（会弄脏柱子），
    两个都更糟。**所以这一条不要「修」**。

  - **50% 是 50/50 的理论期望**，天然是「欧／不欧」的分界；**35% 是「明显低于随机」**，标出真的差的段落。
    中间那档早先是**中性灰**（`#8A8A96`），换红绿蓝后改成绿色：灰的问题是它在深色底上
    和红柱对比只有 1.15，被柱子淹没（用户原话「这个折线图有 3 个颜色么？我看不太清」）。
  - **跨界线段整段按较高一端的档位着色**：一段连线两端是 30% 和 40% 时，整段取 `Math.max` 落档。
    「这段有没有跨过上一档」比「这个点落在哪档」更贴近读数习惯。
  - **不能用 `line` + `visualMap` 实现**：`visualMap` 的 `pieces` 按数据点判色，
    ECharts 会在相邻两点之间用两端颜色做渐变过渡，做不到「整段同一色」。
    必须用 `type: 'custom'` 自己画：每条线段由左端点负责画，圆点按自身值单独定色。
  - 折线 `z` 要高于柱子（3）、低于头像（4）与多金点（5），否则会被柱体压住。
  - 折线的蓝（`#7FB4FF`）与「蓝＝极欧 ≤ 40 抽」的柱（`#3F7BFF`）同色相、不同亮度，靠亮度区分。
- **柱顶头像栈**：每根柱顶上摞该轮涉及的所有金（**头像 22px，层间距 23px**），**先出的在上、后出的在下**。叠放顺序是「歪出角色 → UP → 十连副金」：歪出的先出，所以在最上层；十连副金在 UP 之后出，所以在最下层。
  **歪出的角色必须画出来**——只画 UP 会让「这一轮歪了谁」在图上消失。实测 27 根 UP 柱里有 13 根带歪出头像，加上 1 个十连副金，柱顶头像总数 = 41 = 全部金数。
- **柱顶总抽数**：写在该柱头像栈的**正上方**，不能被头像压住；头像层数不同，所以每根柱的偏移量要按自己的层数算。
- **两个坐标轴都固定，不按数据自适应**（`config.numbers.axisPullsMax` / `axisWinRateMax`）：
  - **左轴（抽数）按频道固定**：角色池 / 常驻 / 独家重映 **0~180**，音擎 / 音擎回响 / 邦布 **0~160**。
    取值依据是「该频道保底 × 2」：一轮 UP 的成本最多是「先歪一次吃保底 + 再吃保底」。
    自适应的问题很直接——基线账号最高柱 159、音擎最高 137，各自缩放后两张图的柱子看起来一样高，
    读者读不出谁更高。固定之后跨账号、跨频道都能直接比。
  - **右轴（不歪率）固定 0~100%**：不歪率的理论范围就是 0~100%，没有按数据缩放的道理。
    固定后 35% / 50% 这些分界线在任何一张图上都落在同一高度，档位读法统一。
    代价是曲线只占下半幅（实测大欧号终值 56.3%、非酋号 48.1%），但那才是真实水平。
  - 早先两个轴都做过自适应（左轴 `ceil((max+18)/30)*30`、右轴「峰值 + 10%」），
    那是把「单图好看」放在了「跨图可比」之上，已废弃。
- **红柱 ≠ 歪**：红是「超出该账号每 UP 均」（非酋），绿/蓝是欧。真正的 50/50 结果看「歪」章（在详情里）。
- **累计不歪率按三档分色**（红→绿→蓝），和柱体同一套语义，见 §3.0 与下方分档表。
  右轴**固定 0~100%**，不按数据自适应（见上条）。早先这里写过「金色折线 + 右轴自适应」，已废弃。
- **右轴下限就是 `0`，和 x 轴基线对齐，不要抬到负值。**
  0% 的意思是「一次都没赢过」，它本来就该坐在基线上。早先试过留 -4% 负余量
  去换「看得见」，结果 0% 那条线被抬离基线，读者反而要猜「这条线到底是不是 0」——
  **不能拿坐标语义去换可见性。**
- **贴底可见性用这三条解决，都不动坐标语义**：
  1) `z` 高于柱子（见下条），否则线被柱体压住，整段消失；
  2) 折线 `clip: false`，描边不裁进 grid，贴底时不会被切掉一半；
  3) 柱子画在线的下面，线在基线附近依然是完整的。
- **折线的 `z` 必须高于柱子的 `z`（柱子默认 2，折线设 3）。**
  两者同级时折线会被柱体压住，曲线一进到柱子范围内就看不见——
  表现为「曲线从中间才开始，前面那几根柱子没有线」。
  用户会以为数据缺失，实际是图层顺序问题。3 高于柱子、低于头像（4）与双金点（5），
  既能整段可见，又不会骑到角色脸上。
  - 两个问题要分清：**z 太低**＝线被柱子挡住（整段消失）；
    **0% 贴底**＝线在柱子外面也看不见（只影响 0% 那几段）。两个都要修。
- **不画版本分隔竖线。** 早先版本用贯穿全图的灰色虚线标版本切换，但柱顶头像是摞在柱子上方的，
  竖线一定会插进头像和总抽数里，噪音大于信息。横轴本身按版本标注（`v1.0` / `v1.1`），分界已经看得出来。
- 横坐标写 `v1.0`、`v2.7`（**带 v**），**同一版本多根柱时只标一次、标在该版本那一段的中间**。
  逐柱都写版本号会变成 `v2.0 v2.0 v2.0` 一片——既读不出它们同属一个版本，也挤掉了相邻真正不同的版本。
  实测 71 轮 UP 的账号，去重前横轴 71 个标签糊成一片，去重后是 14 个版本号。
- **版本号的画法（用户定死的口径，改之前先问）**：
  - **版本号画在「线里面」**，也就是夹在 x 轴与横线之间（`textY = 轴 + 11`，横线在轴下 22）。
    读者看到的是「一条横线 + 两端竖虚线，版本号被框在中间」，而不是版本号飘在线外面。
  - **多柱版本**：一条横线 + **两端竖虚线**把版本号框住，版本号**真正居中**。
    居中必须取 `(首柱 x + 末柱 x) / 2` 自己算——`axisLabel` 只能把文字挂在某个柱心上，
    2 根柱的中点落在两根之间（x.5），挂哪一根都会偏半格。所以版本号、横线、虚线全部由 `custom` 自绘。
  - **单柱版本**：只显示版本号，**不画任何线**。单柱没有「跨度」，两端竖虚线会退化到同一个 x 上（看起来像一条粗线），
    横线也没有左右可延伸。早先试过给单柱加一个「横托」，结果托的宽度和实际柱宽对不上，看起来是歪的。
  - **只有一个数字时不要偏移**：单柱版本的版本号必须正对柱心，左右都不能偏。
  - 竖虚线要够长（实测 ≥18px）才画得出虚线感：短了只剩一段 dash，看起来还是实线。
  - 竖虚线只提示范围边界，**不做封闭括号**（早先做过开口朝上的 U 形，用户否掉了）。
- **图例固定 4 条，单行**：红＝超出均值 · 深色段＝歪掉的抽数 · 蓝＝极欧 ≤ 40 抽 · 绿＝欧。
  只留「光看图看不出来」的语义。**不要**把「柱顶＝总成本」「柱内＝各段抽数」「头像先出的在上」这类自解释的东西写成图例——那会把注脚变成说明书。
  行尾原来的灰字「官方接口 · N 条 S 记录」（`copy.legendTail`）已按用户要求删除，图例不再有右侧尾注。
- **折线三档不进图例**：折线靠自身颜色（红/绿/蓝三档）和右轴刻度就能读，tip 里也已经写了完整链路。
  两条都写进图例会让注脚变成说明书。实测去掉后图例只剩 4 条，单行放得下。
- **首屏无滚动**：1440×900 与 1280×800 都要首屏装下、图例单行；详情在第二屏，首屏底部不露出详情边线。
- **两张卡必须等宽、左右边界对齐**。主图在 `.screen` 内（该容器自带左右 20px 内边距），
  详情卡在 `.screen` 之外，**必须补同样的水平外边距**（`margin: 0 20px`），否则详情会顶到视口两边。
- **详情行悬浮高亮的是这一行自己**，不是联动上方主图。
  - 用 `:hover` 给整行加淡背景（`rgba(240,240,241,.07)`），左右各外扩 6px，
    让高亮像一条整宽的横带，而不是只包住图标和条（后者看起来像「选中了图标」）。
  - 同时把条轻微提亮（`filter: brightness(1.12)`），行背景和条一起强调。
  - 纯 CSS 即可，不要写 JS 去操作 ECharts —— 详情行和柱子数量本来就不一一对应
    （逐金 41 行 vs 主图 27 柱），跨面板联动只会误导。
- **主图可折叠，默认展开。** 折叠是为截图服务的：把主图收起来后 `.screen` 不再撑满 100vh，
  详情顶上来，顶部信息 + 详情能进同一屏（实测 1440×900 下一屏可见 20 行详情）。
  - 折叠**只收外层容器高度**（`.chart-main { height:0; overflow:hidden }`），
    **绝不对 `#chart` 用 `display:none`**——那会让 ECharts 读到 0 尺寸，展开后画布塌掉。
  - 展开时**不要重建图表**，只需 `chart.resize()`。`#chart` 的 display 始终是 block，
    容器尺寸恢复后 resize 即可还原，实测 `instH` 全程不变。
  - 按钮放在面板头右侧（`.panel-meta` 之后），箭头 0° ↔ 180° 旋转，文案「收起 / 展开」。
- **面板标题要垂直居中**：`.panel-head` 用 `align-items: center`，不要用 `baseline`——
  标题（15px 粗体）与右侧灰字（11px 等宽）基线不同，用 baseline 会让标题视觉偏下约 5px。

### 3.2 tooltip（axis trigger）

formatter 返回的是**纯文本多行**，必须显式保留换行：`extraCssText: 'white-space: pre'`
（ECharts 默认会把 `\n` 折叠成空格，表现为「换行没了」）。

```
猫又 → 南宫羽                  ← 歪出/副金在前，UP 在后；无歪时只写 UP 名
卡池 v2.7 · 2025-03-15 21:34   ← 版本后接该 UP 出金时间（record_time 转本地时区）
总共 44 抽，直出                ← 未歪
总共 52 抽，大保底，上个池子歪了「猫又」   ← 保底获得（guar）
总共 108 抽，大保底，37 抽歪「11号」      ← 歪了
本发十连多金                    ← 仅该发是多金；逐金分档见 §5
似非实欧，白赚大保底             ← 十连副金且本轮直出
累计不歪率 50%                  ← 永远最后一行
```


### 3.3 垫抽（保底进度）

垫抽 = 「离下一个 S 还垫了多少抽」，来自官方 `type_stats[].next_s_cur_times`。数据一直在落盘，
但过去 0 处展示——而这恰恰是玩家最想看的数。

- **只在第二屏「抽卡详情」里出现，作为正文的一行**，造型照官方调频页：
  **左边金色问号方块**（下一个 S 未知）+ **右边绿色斜纹条**，条内写 `已垫 N 抽`。
  **条右侧不要写 `/90`**：保底上限属于悬浮才需要的细节，常驻显示会把一行变成三个数字，
  反而看不清主次。上限只在 tip 里出现。
- **主图（抽卡总览）不放垫抽。** 主图讲的是「历史每一轮的成本」，垫抽是「当前这一档的状态」，
  两种时间视角混在一个面板头里会让人以为柱子也算进了垫抽。
- **不要放在面板头上**。详情头的横向空间要挤 6 个频段 tab + 勾选框 + meta，
  再塞一条进度条，两边都看不清；而且垫抽和下面的金条是同一套「长度＝数值」的读法，放正文才连贯。
- **放在最新版本组内部的第一行**，不是列表外面。外面那层没有版本括号的缩进
  （1px 括号 + 7px gap + 版本号宽度 ≈ 42px），放外面问号块会比下面的头像整体左移 42px，一眼看出没对齐。
- **上边距要比普通行大（8px）**：这一行紧贴 tab 下划线，26px 的问号方块会被那条金色下划线视觉压住。
- **不要给这一行加分隔线**（`border-bottom` / `<hr>`）。它就在 tab 下划线正下方，
  再加一条横线会被读成「当前频段的第二个下划线」，而且横线铺满整行、比 tab 下划线长得多，像页面分割线。
  用 `margin` 留白分隔即可。
- **该频段进度为 0 时不画**（如独家 / 音擎：刚出完金或没垫）。显示一条空条只会让人以为坏了。
- **空频段也要画**（如音擎回响：垫了 12 抽、一金未出）。只写「这个频段还没有 S 级记录」
  等于把唯一有信息量的数藏起来。
- **保底上限在 `config/report.json` 的 `channels[].pityCap`**，按频段不同（见 `references/api.md` §5）：
  常驻 / 独家 / 独家重映 90，音擎 / 音擎回响 80，邦布 80。
  **不要用 `new_s_max_times`**：那是官方 UI 的区间展示值，不是硬保底
  （实测常驻该值 32，而该频道最长出金间隔是 80）。
- **剩 ≤ 10 抽时条变红**（`.pity-row[data-near="true"]`），表达「马上就要出了」。
- **悬浮显示「保底上限 + 上一个 S」**：行内只有「已垫 58 抽」，读者要知道还差多少、
  从谁开始垫的，都在 tip 里：`已垫 58 抽，还差 32 抽到保底（90 抽保底）` + `上一个 S：啜泣摇篮（v3.1）`。
  整条频道还没出过金时后半行不出现。
- **口径只在 `build-report.mjs` 算一次**：`{cur, cap, remain, pct, last}` 由构建产出，前端只负责画。

## 4. 称号（`config.report.json` → `titles.tiers`）

基准：角色池每 UP 期望 = 62.5 抽/金 × 1.5（50/50）= **93.75 抽**。

**大标题要能悬浮查看完整档位。** 鼠标移上去显示全部 10 档区间，**当前档加粗高亮**，第一行写清本账号的判定：

```
每 UP 均 87.9 抽 → 欧气满满大欧皇

≤ 62.5      终极无敌至尊欧皇
62.5 – 80   万里挑一至尊欧皇
80 – 90     欧气满满大欧皇      ← 这一行加粗 + 主题金色
90 – 95     欧气附体小欧皇
95 – 99     欧非守恒
...
> 125       终极无敌至尊非酋

按「角色池每 UP 均（含歪）」判档
```

- 区间文案要**算出来**（`prev ~ maxPullsPerUp`），不要在提示里手写死。
- 当前档靠比对 `tiers[].name` 命中，不要按索引猜。
- **加粗 + 颜色表示命中的那一档**，不要用 `▶` 之类的符号前缀。
- 光标用 `pointer`（与 Tag、详情行一致，同是手形），**不要用 `cursor: help` 的问号光标**。
- 标题要给出可悬浮的**视觉暗示**，但**不要用虚线下划线**（像超链接，观感廉价）：
  hover 时用主题色柔光（`text-shadow` + `brightness`）即可。
- 气泡样式与图表内 tip 保持一致（同一个 `.tip` 组件）。
- 因为要加粗，这条提示走 `data-tip-html`（内容需转义后再拼 `<b>`）；其余提示仍走纯文本 `data-tip`，避免 XSS 面。

档位来自 2026-11 收集的 12 条工坊「抽卡总结」样本拟合，**不是人群百分位**；不歪率只是强相关，不能当判据。

| 每 UP 均 | 称号 | tone |
|---|---|---|
| ≤ 62.5 | 终极无敌至尊欧皇 | lucky 金 |
| ≤ 80 | 万里挑一至尊欧皇 | lucky 金 |
| ≤ 90 | 欧气满满大欧皇 | lucky 金 |
| ≤ 95 | 欧气附体小欧皇 | lucky 金 |
| ≤ 99 | **欧非守恒** | neutral 灰白 |
| ≤ 105 | 欧气不足小非酋 | unlucky 红 |

改档位只改 `config/report.json`，`tiers` 按 `maxPullsPerUp` 升序、最后一项用 `null` 兜底。
`scripts/build-report.mjs` 会按顺序取第一个满足的档位。

**顺序必须是单调阶梯：抽数越少越欧、越多越非，中间不许回头。**
踩过一次：`欧非守恒`（neutral）原本排在 ≤95 档，而 `欧气附体小欧皇`（lucky）在 ≤99 档，
于是 89 抽叫「大欧皇」、95 抽叫「守恒」、99 抽又叫「小欧皇」——抽得越多反而越「欧」，
用户直接问「小欧皇咋比欧非守恒还差」。现在 `欧非守恒` 落在 99 档，
作为最后一个欧档（95 `欧气附体小欧皇`）与第一个非档（105 `欧气不足小非酋`）之间的**分水岭**。

**`tone` 必须真的渲染色差。** 这里也踩过：`.title-name` 只有一条写死 `color: var(--accent)` 的规则，
**没有任何 `[data-tone]` 分支**，而 `charts.js` 一直在往 `#h1` 写 `data-tone`——写了没人读，
结果「至尊欧皇」和「至尊非酋」渲染成同一个金色，称号这行字自己说不出运气好坏。
现在三档色相明确不同（实测计算值）：

| tone | 色值 | 用途 |
|---|---|---|
| lucky | `rgb(245,192,74)` 金 | 欧，沿用 `--accent` |
| neutral | `rgb(242,242,244)` 灰白 | 守恒，不偏袒任何一边 |
| unlucky | `rgb(255,95,109)` 红 | 非，复用 `--bad` 与非酋档同语义 |

颜色全部走 CSS 变量（「改配置就生效」的约定），不在 CSS 里另写死色值。

## 5. 标签（`config/report.json` → `tags.rules`）

规则是**数据驱动**的：每条 rule 有 `kind`（`metric` / `series` / `event` / `round`）、条件、配色和提示模板。条件不满足就不出现，不要为了好看硬凑。

| 标签 | 触发 |
|---|---|
| `欧气附体` | 十连双金 ≥ 1 次，或极欧柱 ≥ 2 根 |
| `运势极佳` | 最长连 UP ≥ 4 |
| `时运不济` | 最长连歪 ≥ 3（负向） |
| `非酋附体` | 每 UP 均 > 110（负向） |
| `代理人 K 连 UP ×N` | 连续直出段；**每个不同长度各出一个标签**，同一长度出现多次才加 ×N；**保底获得要打断连 UP** |
| `代理人 K 连歪 ×N` | 连续先歪段；同样是每个长度各出一个标签 |
| `十连双金 ×N` / `十连 3 金` / `十连 4 金` | 十连多金组，**按一组的金数分档**，不写人名；**tone 用 positive（金）** |
| `似非实欧 ×N` | 先歪但总抽 < 该账号每 UP 均；蓝色 |
| `非酋翻身记` | 曾经真掉进非酋档（谷底 `< 35%`）、现在爬出来了（终值 `>= 35%`）、涨幅 `>= 15pp`；tip 写「最低 / 最高 / 当下」三点，不写涨幅 |
| `薛定谔的非酋` | **曾经**在非酋和欧之间来回横跳（完整窗口序列内非↔欧切换 `>= 2` 次）；中性灰 |

### 5.2 轨迹标签（`非酋翻身记` / `薛定谔的非酋`）

这两个标签看的是**累计不歪率的走法**，不是终值。终值只差 8pp 的两个号，走法可以完全相反。

**为什么不能只看终值**：实测基线账号 48.1%、多金账号 56.3%，只差 8 个百分点，
但基线账号是「从 14.3% 一路爬上来」，多金账号是「一路在 70% 和 20% 之间起伏」。

**横跳的分界线不是 50%**。这是最容易搞错的一点：50% 是**小欧和大欧**的分界（50~65 小欧、>= 65 大欧），
两边**都是欧**，在 50% 上下浮动不代表横跳。真正的横跳是**在非酋和欧之间来回**：
`nonEdge`（35%，非酋档上界）以下算非、`euroEdge`（50%，理论期望）以上算欧，
中间那条「薛定谔」带（35~50）两边都不算 —— 它本来就是「还看不出来」的地带，在里面游荡不算横跳。

**横跳必须在滑动窗口上算，不能看累计值**。累计是全程平均，早年的坑会被越摊越淡：
多金账号的累计谷底是 42.9%，**从没进过非酋档**，按累计值算横跳次数是 0 —— 但它显然在来回跳。
把窗口收到 10 轮就看出来了：窗口内胜率一路从 70% → 20% → 80%（实测切换 2 次）。
注意这是**该号 v1.2～v1.4 那一段的历史**，不是它现在的状态——第 27 轮之后窗口一直稳定在 50~80%。
所以 `winRateShape()` 在 `rollingWinRate()` 的序列上数切换，而标签文案必须带出版本区间与距今轮数。

**`minSamples` 门必须加**：前几轮的累计值是噪音。1 轮 0%、2 轮 50% 这种极值会把谷底拉到 0%，
于是每个新号都能自称「曾是非酋」，标签直接烂大街。默认从第 5 轮起算
（基线账号前 3 轮都是 0%，排除后谷底落在第 7 轮 v1.5 的 **14.3%**）。

| 实测 | 谷底 | 峰值 | 终值 | 非↔欧切换 | 命中 |
|---|---|---|---|---|---|
| 基线账号（27 轮） | 14.3% @v1.5 | 50.0% @v2.7 | 48.1% @v3.3 | 1 | `非酋翻身记` |
| 多金账号（71 轮） | 42.9% @v1.4 | — | 56.3% | 2 | `薛定谔的非酋` |

**两条标签不互斥**（用户明确要求）：一个号可以既翻过身、又一路来回跳。

#### `非酋翻身记` 的 tip 写三点，不写涨幅

用户原话：「不用写涨百分比，可以加下最高不歪率的描述。即最低，最高，当下」。

```
累计不歪率
最低 14.3%（v1.5）
最高 50%（v2.7）
当下 48.1%（v3.3）
```

- **一行一点，不要挤成一行**。挤成一行时读者要在一长串里找「最低 / 最高 / 当下」三个词；
  竖排之后三项一眼扫完。用 `\n` 分段即可，气泡是 `white-space: pre`，天然保留换行
  （实测四行气泡 128×87px，无横向溢出）。
- **涨幅是派生量，不进文案**。`+33.8pp` 这种数字读者要自己反推才知道曲线的形状，
  而且「涨了 33.8pp」既可能来自 14.3%→48.1%，也可能来自 20%→53.8%，两种轨迹观感完全不同。
- **必须给峰值**。只写最低和当下，看不出中间冲得多高：基线账号当下 48.1% 反而**低于**自己的峰值 50%，
  只报「从 14.3% 涨到 48.1%」会让人以为它一路向上、正在最高点。
- 三点都带版本号，读者能回图上核对位置。峰谷的下标都取自 `pts`（已跳过 `minSamples` 轮噪音），
  不拿全序列首个值冒充——前几轮的 0% 会把谷底拉成 0%，让每个新号都「曾是非酋」。
- 对应指标：`winRateTrough` / `winRateTroughVersion`、`winRatePeak` / `winRatePeakVersion`、
  `winRate`（终值）/ `winRateFinalVersion`。
- **判据里的 `winRateRise` 保留**，它只是不再出现在文案里：
  涨得不够多（`< 15pp`）说明是噪音回弹，不是真的翻身，这个门槛不能因为不写涨幅就一起删掉。

#### `flips` 是历史事件，不是当前状态

`flips` 在**完整窗口的全序列**上统计（`rollingWinRate(bits, window).slice(window - 1)`，
从第 `window` 轮一直数到最后一轮），**不是只看最近几轮**。所以这个标签描述的是「**曾经**来回过」。

实测多金账号：2 次 flip 落在第 20 轮和第 27 轮（共 71 轮），**距今 44 轮**；
按最近 30 个窗口算，flips 早已回到 0。

因此文案**必须**带出版本区间与距今轮数：

> `不歪率曾在非酋和欧之间来回横跳 2 次（v1.2～v1.4），最近一次在 44 轮前`

- **不许写「近期」**。写着「近期胜率在来回跳」，实际指的是 44 轮前就结束的事，
  读者会以为这个号现在还在剧烈波动——措辞把历史事件说成了当前状态，是**事实性错误**。
- **必须点明是「不歪率」**，且逐条明细里要写「**近 N 轮**不歪率」，不能只写「窗口」或光秃秃一个百分比。
  「窗口」是算法内部说法（`rollingWinRate()` 的窗口长度），读者不知道在量什么；
  不写「近 N 轮」则会被当成**累计**不歪率，拿去和顶部 KPI 的 56.3% 比，然后发现对不上——
  这两个本来就是不同的量（多金账号累计谷底 42.9%，近 10 轮却能掉到 20%）。
- 对应指标：`winRateFlipFromVersion`（首次 flip 的版本）、`winRateFlipToVersion`（末次 flip 的版本）、
  `winRateFlipToAgo`（`总轮数 - (末次 flip 轮索引 + 1)`）。
- **下标必须换算回轮索引**：遍历的是 `slice(window - 1)` 之后的切片，
  循环变量是「切片内第几个」，真实轮索引是 `i + (window - 1)`。
  用错会整体前移 9 轮——实测多金账号会算成 v1.1～v1.2、53 轮前，正确的是 v1.2～v1.4、44 轮前。

#### tip 必须逐条列出每次横跳的具体数值

只写「来回 2 次」看不出**跳幅**：从 55% 掉到 30% 再弹回 52%，和 49%↔51% 来回蹭，
次数一模一样，含义完全不同。所以 tip 第二行开始逐条列出每次 flip：

> ```
> 不歪率曾在非酋和欧之间来回横跳 2 次（v1.2～v1.4），最近一次在 44 轮前
> v1.2 第 20 轮 欧 → 非：近 10 轮不歪率 50% → 30%，最低 20%
> v1.4 第 27 轮 非 → 欧：近 10 轮不歪率 30% → 50%
> ```

每行四个必填项 + 一个条件项：

| 项 | 来源 | 说明 |
|---|---|---|
| 版本 | `charRounds[flip.idx].version` | 「哪一版」 |
| 轮次 | `flip.idx + 1` | 「第几轮」，1 基（用户数轮次从 1 开始） |
| 方向 | `from` / `to`（±1） | 汉字「欧 → 非 / 非 → 欧」，不用箭头字符（等宽字体下宽度不稳，多行会歪） |
| 读数 | `prevWinRate` → `winRate` | **两侧读数**，且必须冠以「近 N 轮不歪率」，见下方 |
| 最低（条件） | `low` | 仅「掉进非酋档」那一条才写，且 `low < winRate` 时才有意义 |

**读数必须写明「近 N 轮不歪率」，不能只写「窗口 50%」。**
`N` 取 `winShape.window`（配置 `numbers.winRateShape.window`，默认 10），**不要写死**。
理由见上一节：不点明指标名读者不知道在量什么，不点明「近 N 轮」会被误当累计值。

**起点必须取「同档最后一次读数」，不能取上一轮的值。**
两次 flip 之间可能隔着几轮薛定谔带（35~50 不计数），上一轮的值未必属于同一个档；
硬拿上一轮的值当起点会写出一个从没真实出现过的数字。
实现上维护 `lastOf = { '-1': ..., '1': ... }`，每次读到有效档位就更新，
flip 发生时取对面那个档位存着的值。

**「最低」只在掉进非酋档的段落里算**：从这次 flip 起向后扫到下一次 flip（或序列结束），取窗口最小值。
这个是横跳里最有信息量的数——多金账号的**累计**谷底是 42.9%（从没进过非酋档），
但 10 轮窗口实打实掉到过 **20%**，只说「掉进非酋档」读不出掉得多深。

指标名：`winRateFlipList`（`\n` 分隔的多行文本，空时为 `''` 而不是 `null`——
tip 模板里 `{winRateFlipList}` 若为 null 会渲染出字符串 "null"）。
气泡是 `white-space: pre`，直接换行显示，不需要 `<br>`。

#### 非↔欧的分界是 35% / 50%，不是 50% 一条线

- `< 35%` 算**非酋**，`>= 50%` 算**欧**，中间的 35~50 属于「薛定谔」带，**两边都不算**（不计数）。
- **50% 是小欧/大欧的分界，不是横跳线**。50~65 小欧、>= 65 大欧，两档都在欧这一侧，
  在 50% 上下浮动不属于横跳——这是最容易写错的地方。
- 判定要求窗口**真的进出非酋档**（`< 35%`），在小欧/大欧之间浮动不算。

阈值全在 `config.numbers.winRateShape`（`nonEdge: 35` / `euroEdge: 50` / `oscillationFlips: 2` / `window: 10` / `minSamples: 5`），改配置就生效。

**标签配色按语义分四档**（`config.report.json` → `tags.rules[].tone`）：
`positive` 金（好运：欧气附体、连 UP）· `negative` 红（坏运：连歪、非酋附体）·
`info` 蓝（极欧柱）· `neutral` 青（预留，**十连多金的记号色，不要拿来当语义色**）·
`shrodinger` 中性灰 `#8A8A96`（「薛定谔的非酋」）· `highlight` 亮金 + 外发光（**最高光事件**）。
注意这个灰**不再**和折线中间档同色：折线中间档已改成绿色 `#5FD98A`（见 §3.0），标签的灰是独立语义。

**两类标签用 `highlight`**：
- **最长的那条连 UP**（`id` 不带后缀的那个）。一个账号同时有 5 连、4 连、3 连时，
  它们同为常规金色，读者看不出哪条是最高纪录。
- **所有「十连 N 金」**。这是整份报表里最罕见的事件，和普通连 UP 同色会被淹没。

**连歪绝对不能用 highlight**。它和连 UP 走同一段代码，同样有「最长的一条」，
若只按 `idx === 0` 提亮，「代理人 7 连歪」这种最霉的纪录会被高亮成主角，语义完全反了。
判据要带上 `rule.tone !== 'negative'`。

**只换颜色不够**：两个金在深色底上只差几个色阶（实测 `#F5C04A` vs `#FFE066`），
必须有同色外发光（`box-shadow` 两层：1px 描边 + 12px 光晕），才一眼看得出主次。

**多金必须按金数分档，不能一律叫双金。** 一组多金的金数由「同秒且 `sort` 差 ≤ 9」的连续金决定，可能是 2 金、3 金，甚至 4 金：

- **统计范围是「角色池 + 音擎」两个频道合并**，不是只算角色池。
  只统计角色池会漏报：实测多金账号角色池 5 组、音擎另有 2 组（一组三金、一组双金），
  漏掉音擎会让标签写「双金 ×4 / 3 金」，正确是「双金 ×5 / 3 金 ×2」。
- **合并前必须按频道分段再各自成组**：`sameTenPull` 判的是「同秒 + `sort` 差 ≤ N」，
  而 `sort` 是**每个频道各自从 1 开始数**的。跨频道的两个金若 `sort` 恰好接近、
  `recordTime` 又落在同一秒，会被误判成同一发十连——不报错，只会凭空多出一组多金。
  所以是两个独立数组各跑一遍 `multiGoldGroups()`，不是先拍平再跑。
- **2 金用中文字「双金」，3 金及以上用阿拉伯数字**（`十连 3 金` / `十连 4 金`）。
  「双」是约定俗成的固定说法，读起来比「2 金」自然；三金、四金没有这种说法，写数字更好认，也省得去数汉字。
- 实测样本：`雅 79 抽 → 1 抽 → 5 抽` 是一发十连出**三金**（v1.4）；音擎也有 `啜泣摇篮 68 → 青溟笼舍 4 → 青溟笼舍 2` 的三金。
- 把三金写成「十连双金」是**事实错误**，不是措辞问题；总数也会错（5 组多金里含 1 组三金时，双金应是 ×4 而不是 ×5）。
- 实现：`multiGoldGroups()` 返回整组，按 `length` 分档落到 `nameTemplate` / `nameTemplate3` / `nameTemplate4`；
  指标侧同时给出 `multiGoldRounds`（总数）、`multiGold2` / `multiGold3` / `multiGold4`（分档计数）、`maxMultiGold`（最大金数）。

- **每个连段长度都要出标签，不能只留最长的。** 账号里同时存在 5 连歪和 3 连歪时，两条都要显示——
  只取最长会让「3 连歪」这个事实在报表里消失。
- **连段标签从 `minK: 3` 起**：`2 连 UP` / `2 连歪` 太常见，没有信息量，只留 3 连及以上。

### 5.1 标签冲突与优先级

标签会撞车，必须去重，否则同一件事说两遍或自相矛盾：

| 冲突 | 处理 |
|---|---|
| `运势极佳`（最长连 UP ≥ 4） vs `代理人 K 连 UP` | 同一件事。有具体连段标签时**丢掉概括标签**（配置 `suppressWhen`） |
| `时运不济`（最长连歪 ≥ 3） vs `代理人 K 连歪` | 同上 |
| `欧气附体` vs `非酋附体` | 互斥。同时成立时**保留负向**（更值得注意），丢掉正向 |

实现：配置数组里**靠前的优先级更高**；`suppressWhen: [id...]` 声明「这些标签存在时我就不出现」。
被丢掉的标签会在构建日志里打印，便于核对。
- **连段提示的格式**：`v1.0～1.1：朱鸢（格莉丝） → 青衣（猫又） → 简（「11号」）`
  - 版本写区间：同版本 `v2.0`，连续区间 `v1.0～1.1`（**尾版本要写全**，`v2.1～2.3` 不能缩成 `v2.1～3`，会被读成「到 v3」）
  - 每一环带出歪出/副金的角色名，写在括号里；直出就只写名字
- **标签直接换行，不裁剪也不折叠。** 标签本身就是结论，藏进 `+N` 等于让用户多点一次才看得到。
  标签行用 `flex-wrap: wrap`；图表区是 flex 撑满的，会让出高度（标签从 1 行变 2 行时图表约少 30px，仍装得下首屏）。
- **光标统一 `pointer`。** 大标题、标签、详情行——凡是能悬浮出提示的都用手形，不要混用 `default` / `help`。
- **只有出现不止一次才写 `×N`**：单次就是 `似非实欧`、`十连双金`，不要写成 `×1`。单次出现时也不加计数后缀。
- **提示文案用玩家话，不要用图表内部术语。** 「极欧柱 N 根」这种说法读者看不懂；要写成
  「十连出过 N 次双金 · N 次在 40 抽内出金」。任何 `柱 / 段 / 轴` 这类词都不该出现在面向读者的句子里。
- 计数类标签 hover 显示具体轮次（版本 + 角色链），用自绘深色气泡（`data-tip` + JS 定位），**不要用原生 `title`**。
- 联动高亮：**反差式**——hover 时把**没命中**的柱子压暗（不是点亮命中的那几根），离开时清空。
  命中集合由 `data-bars`（索引区间 `12-15;18-21`）或 `data-gold-sorts`（多金，见下节）给出，
  再 `dispatchAction({type:'highlight'})` 给命中的柱加白描边。**不要改回 markArea**，原因见 §6 的多金小节。
  **十连多金标签走另一条通道 `data-gold-sorts`**，原因见下方「多金标签的索引不能复用 `data-bars`」。

## 6. 第二屏：抽卡详情

  空频段显示「这个频段还没有 S 级记录」，上下各留 40px 白（改前是「在剩余空间里垂直居中」）。
  - **改前 vs 改后**：
    - 改前 `height: 480px` + `overflow-y: auto` + `overscroll-behavior: contain`。
      理由当时是「切频道不跳」：各频道行数差异极大（独家 41 行、音擎回响 0 行），

- **面板右上角只写 `N 金 · 每金 X 抽`**（合并模式写 `N 次 UP · 每 UP X 抽`），**不要**再追加「从新到旧」之类的排序说明——排序是固定行为，不必写出来占位置。
- 版本括号：相邻同 `version` 的行归为一组，组左侧 1px 方括号，**括号右侧写版本号**（9.5px mono 灰字），组间留 5px。
- 行悬浮 tip：第一行是 `名字 · 本体|影画N`（只给角色，见下），第二行 `vX · 出金时间`；
  第三行逐金写 `距上一个金 N 抽 · UP|歪`（该频道首个金写 `本频道首个金，N 抽`）、
  合并写 `本轮 N 抽 ＝ UP a + 歪 b` 与 `歪出：名字 b 抽`，
  无歪写 `本轮 N 抽 · 无歪`；常驻、邦布不标 UP/歪。

  - 名字本身已带 `「」` 的（如「11号」）**不要再套一层**，否则会写出 `「「11号」」`。
- 图标全部本地化：`assets/report/icons/items/<item_id>.png`（64px），失败回退 `assets/report/icons/items/_fallback.png`，**不裂图、不引 CDN**。

### 6.1 左右两栏：右栏是角色维度汇总

详情区是**左右两栏**（`.detail-body` 是 grid）：左栏是上面那一整套逐金列表，**一行没动**；
右栏是按角色聚合的汇总。用户原话：「左边保持现在的，右边是角色纬度的汇总，
看一个角色是几影画，一共用了多少抽，歪了几次」。

**两个同级栏标题并排在同一行**：「抽卡详情」（左）…… 「代理人汇总」（右），各贴自己那一列。
频段 tab / 「真实抽数」/ meta 与「抽卡详情」**同一行**（`.detail-head-main`）——
用户看过「挪进左栏内部第一行」的版本后要求挪回来（「还是放到跟它同行试试」），详见 §6.2 ③。
790 及以下这一组折行（tools 掉到第二行），不缩字号、不裁文字。

#### 6.2.0 头部这一行的**垂直基线**：`align-items: baseline`，不是 `center`

三处容器的 `align-items` 决定「标题、tab、勾选框」这一行里谁跟着谁对齐。**只能是 `baseline`**：

| 选择器 | 属性 | 改前 | 改后 |
|---|---|---|---|
| `.detail-tools` | `align-items` | `center` | **`baseline`** |
| `.merge-toggle` | `align-items` | `center` | **`baseline`** |
| `.merge-toggle input` | `align-self` | （无，继承 `center`） | **`center`** |
| `.merge-toggle` | `font-size` | `11.5px` | **`12px`**（与 `.detail-tab` 统一） |

**`center` 为什么会歪**：`align-items: center` 下，这个 flex 行的「行内基线」取的是
子项盒子的中线，而不是文字的基线；而 checkbox 是 **13×13** 的替换元素、比旁边 11.5px 的小字高，
于是整组按 checkbox 的中线居中，**文字被抬起来**。实测（改前，1440）：
「显示真实抽数」文字 bottom **900.5**，「抽卡详情」标题文字 bottom **904** —— 差 **+3.5px**（勾选框那行偏高）。

改成 `baseline` 后文字之间按真实基线对齐；checkbox 自己用 `align-self: center` 留在行内居中、
不参与基线计算。**字号顺带统一到 12px**（原来 11.5px 比 tab 的 12px 小半号，基线下这半号会变成肉眼可见的错位）。

改后实测（`fixtures/baseline`，标题文字 bottom −「真实抽数」文字 bottom）：

| 视口 | 改前 dMerge | **改后 dMerge** | headH / mainH（改后） | 一行 |
|---|---|---|---|---|
| 721 / 760 | −23（tools 折第二行） | −25（同样跨行） | 61 / 46 | 否 |
| **790 / 800 / 1000 / 1440** | **+3.5** | **0** | **44 / 29** | **是** |

`dTab`（标题 bottom − 首个 tab bottom）六档全部 **0**，改前改后一致，没被碰坏。

> **790 / 800 回到一行是「文案变短」的功劳，不是这四条 CSS 改动的功劳——别记反了。**
> 实测拆开看：四条 CSS 改动**全部应用**、但按钮名仍是「显示真实抽数」时，
> 790 与 800 的 `.detail-head-main` 仍是 **46px（两行）**，只有 1000/1440 是一行（实测，见下表）。
>
> 横向数字（1440 实测 `getBoundingClientRect`，`.detail-tools` 宽度 / 其中文字宽度）：
>
> | 文案 + 字号 | toolsW | 文字宽 |
> |---|---|---|
> | 老文案「显示真实抽数」，11.5px | 87 | 72 |
> | 老文案「显示真实抽数」，12px | 90 | 72 |
> | 新文案「真实抽数」，11.5px | 64 | 46 |
> | **新文案「真实抽数」，12px（当前）** | **66** | 48 |
>
> 文案缩短净省 **23~24px**（87→64、90→66），正是它让 790/800 从「差几个像素」变成放得下。
> 字号从 11.5 涨到 12 反而多占 **3px**，被文案省下的量盖过去了。
>
> **归因只有文案一处，别写成「文案和基线一起起作用」**（隔离验证过）：
> 只上 `baseline` 三项、字号保持 **11.5px**（即不动字号），toolsW 仍是 **64**，790/800 **依旧一行**
> ——基线改动与折行无关，它只解决 ±3.5px 的垂直错位。
> 反过来，只把按钮名改回长的（CSS 保持新版）→ toolsW **90**，790/800 立刻重新折行。
> 所以：**790/800 的一行 = 文案那 23~24px，仅此一项**；把按钮名改回长的会立刻退回两行；
> 只回退字号（保持新文案）仍是 64，仍是一行。
>
> `--detail-head-gap` 只是**边界条件**，不是主因：当前值 6px（≤840 断点），文案缩短后 790 有余量。
> 实测把 gap 放大到 **12px 时 790 仍是一行**、**14px 才折行**（800 在 14px 下仍是一行）。
> 也就是说间距是「差几个像素时的安全垫」，别把它记成一行成立的原因，也别为了更宽松去加大它。

**验收口径（量的是文本节点，不是容器）**：`dTab` / `dMerge` 都用
`Range.selectNodeContents()` 包住第一个非空文本节点再 `getBoundingClientRect()`，
不要量元素盒子的 `bottom` —— tab 自带 `padding: 4px 10px 6px`、label 也带 padding，
量盒子会把「留白」算成偏差。


两处列定义共用同一个变量 `--detail-cols` / `--detail-gap`（声明在 `.detail-panel` 上），
各断点只改这个变量。**不要给 `.detail-head` 和 `.detail-body` 各写一份列定义**——分开写必然漂移，
症状是「代理人汇总」标题跟它下面那一栏错开几个像素。

**两栏不联动。** 左栏跟着频段 tab 走；右栏是**全账号跨全部频段合并**的独立汇总，
切 tab 右栏一行都不变（实现上就是只画一次，`renderDetailChars()` 从 `init()` 调，
不在 `renderDetail()` 里调——那样每次切 tab 都会重建 DOM，把右栏滚动位置重置掉）。

右栏按「这个角色有没有当过 UP」分成两类，显示的东西不一样：

| | 影画 | 一共多少抽 | 歪 | 悬停 tip |
|---|---|---|---|---|
| **UP 角色** | ✅ | ✅ 它**各轮 `total` 累加** | ✅ 追它时歪过几轮 | 每次获得一行 + 末行均抽 |
| **非 UP 角色** | ✅ | ❌ 不显示 | ❌ 不显示 | **逐影注明每只的来源**（常驻 / 抽哪个 UP 时歪出 / 十连副金） |

**UP 角色**：

| 指标 | 算法 | 口径要点 |
|---|---|---|
| 影画 | 全部频段 `appearances - 1` | 第 1 只给 **0 影**。**这是按记录出现次数反推的，不是游戏内影画等级**：出现 8 次会显示 7 影并标「超上限」（`numbers.portraitsCap = 6`），因为 6 影后继续抽只会重复获取 |
| 一共多少抽 | **该角色每一轮那一轮的 `total` 累加** | 一轮 `total` = 期间歪出的抽 + 这一只自己的 `count` + 十连副金。雅 3 只 = 152+154+78 = **384 抽** |
| 歪 N 次 | 走轮次模型：`round.off > 0` 或 `round.guar` 的轮数 | **不是 `count(is_up === false)`**。`is_up === false` 的意思是「这个角色是被歪出来的」，不是「这个角色输了 N 次 50/50」——按条数数会让猫又这种常驻角色显示「歪 2 次」，语义正好反了 |

**抽数为什么必须用轮 `total`，不能用 UP 那条的 `count`**（这条也写错过一次）：
大保底那一只必须把前面歪掉的抽算进成本，否则「为了拿到它花了多少」会系统性偏低。
雅的两轮实证（`fixtures/baseline`，独家频段）：

| 雅第几次 | 期间歪出 | off | 自己 up | 该轮 total |
|---|---|---|---|---|
| 1 | 珂蕾妲 77 | 77 | 75 | **152** |
| 2 | 丽娜 77 | 77 | 77 | **154** |
| 3 | 无（直出） | 0 | 78 | **78** |
| | | | | **384** |

只取 `count` 会算成 75+77+78 = **230**，凭空少掉 154 抽——那正是「为了拿到它先歪出去的成本」。

**自洽校验（构建期 fatal，防的就是口径再被改错）**：右栏所有 UP 角色的 `pulls` 之和必须等于
**独家 + 独家重映的官方已抽数**（`total_count − next_s_cur_times`）：
baseline = `GACHA_TYPE_CHARACTER_UP` 2372 + `GACHA_TYPE_CHARACTER_RETURN`(90−14=76) = **2448**。
实测两套数据集都闭合，19 个 UP 合计 2448，一抽不差。

闭合在数学上是恒等的：这两个频道里每一抽都必然落在某一轮里（轮 = 一次 UP 获得及其前缀），
所以「轮 total 累加」等于官方总抽数；换成别的口径就一定不等。
**误用「只取 up 的 count」时合计只有 1759**（掉 689 抽），构建直接失败并点名：

```
✖ 右栏 UP 角色抽数合计 1759 ≠ 独家频段 + 独家重映 官方已抽 2448：
  抽数口径错了（必须是「该角色各轮 total 累加」，含期间歪出的抽，不能只取 UP 那条的 count）
```

范围只取 `has5050 && kind === 'avatar'`：右栏只统计角色，UP 轮也只在这两个频道产生；
音擎 / 常驻 / 邦布不参与。

**非 UP 角色只显示影画。** 用户原话：「非 UP 角色显示几命即可」。这些角色从没当过 UP：
给它们算「一共多少抽」没有意义（抽数属于把它歪出来的那个 UP 角色），
而「歪了几次」在它们身上恰好是反的（`is_up === false` = 它是被别人歪出来的）。
数据层仍保留 `pulls` / `lostOut` / `lostOutMain` / `lostOutSide`，**界面不渲染**。

### 非 UP 角色的 tip：逐影注明来源

用户原话（推翻上一版）：

> 珂蕾妲•5影・没当过 UP
> 这 tip 不好，不要写 "没当过 UP"，然后换行注明下它的每一影的分别来源，
> 是常驻多少抽出的还是抽哪个 up 多少抽歪的

改前只一行 `珂蕾妲 · 5 影 · 没当过 UP`，六个非 UP 角色全都是这一种写法。
改后：第一行 `珂蕾妲 · 5 影`，下面每影一行，措辞按**真实来源**分流：

```
珂蕾妲 · 5 影
本体：抽「雅」时 77 抽歪出 · v1.4
影画1：常驻 6 抽 · v1.6
影画2：抽「橘福福」时 15 抽歪出 · v2.0
影画3：常驻 79 抽 · v2.3
影画4：抽「叶瞬光」时 80 抽歪出 · v2.5
影画5：抽「菲欧妮」时 21 抽歪出 · v3.3
```

**为什么去掉「没当过 UP」**：那句话只否定一件事（它不是 UP），却不回答「那它哪来的」——
而来源本来就在数据里。上一版写它的理由是「这 6 个并不都出现在常驻频段，写『常驻角色』会给出假来源」，
那个顾虑成立，但推不出「于是只写一句否定」：逐条点名才是既准确又有信息量的写法。

**三种 `kind` 与措辞的对应**（数据层 `charSummary().sources[].kind`）：

| `kind` | 数据来源 | 措辞 | 注意 |
|---|---|---|---|
| `perm` | 常驻频段（`kind === 'permanent'`）的 golds | `常驻 N 抽` | **N 是「距上一个金」的抽数，不是获取成本** |
| `lost` | `round.losts`（抽 UP 时歪掉的） | `抽「X」时 N 抽歪出` | N 是那一金自己的 `count` |
| `side` | `round.side`（十连里跟在 UP 后面的副金） | `抽「X」时十连副金` | **不能写「N 抽」** |

**常驻 `N` 的口径差异必须记住**：常驻没有轮次模型，每一金的 `count` 都是**相对上一金的间隔**，
累加它没有意义（不是「为了拿到它花了多少」）。措辞写「常驻 N 抽」而不是「N 抽抽到」就是为了不说成成本。
角色池的 `N` 才有「这一发花了多少」的含义，因为它落在一个轮次里。

**十连副金为什么单独措辞**：`side` 的 `count` 实测**恒为 1**（十连里排在 UP 后面的那一金，
距上一个金只差 1 个 `sort`）。写「1 抽」会被读成「1 抽就抽到了」，与事实相反——
它其实是「同一发十连里附带出来的」。实测反例：猫又影画3 是抽南宫羽时十连副金，
若按 `count` 写就是「1 抽」，读者只会觉得邪门。

**日期省略**：UP 角色的 `gains` 每行带 `· 2024-12-18`；非 UP 这里**不带日期**。
一行已经有「抽「菲欧妮」时 21 抽歪出 · v3.3」，再加 11 个字符会顶到 `.tip` 的
`max-width: 420px`（`white-space: pre`，超了是**横向裁掉**不是折行）。
版本号足够定位到时间段；用户问的是「哪来的」，不是「哪天」。
实测最宽一行「「11号」影画1｜抽「仪玄」时 29 抽歪出 · v2.0」渲染宽 **242.2px**，离 420 还有 177px 余量。

**兜底**：`sources` 为空、或条数 ≠ `appearances` 时，**退回纯摘要** `珂蕾妲 · 5 影`，
不输出半截列表——半截列表比没有列表更容易被当成完整答案。
不能返回空串：空 tip 会让 hover 出一个空气泡。

## 为什么要留占位（这条被改错过一次，别再反过来）

阶段 ③ 落地时曾试过「只在歪过时才 append `.detail-char-lost`，没歪完全不产生元素」，
理由是「emoji 反正紧跟文字、行尾后面没有要对齐的列，占位白吃一格 gap」。
**这个理由站不住**，实测把它否掉了：

| 写法 | `.detail-char-lost` 数量 | UP 行结构模式 | 有歪 / 没歪同构 |
|---|---|---|---|
| **空 span 占位**（现在） | **19**（19 只 UP 全有） | **2 种**（差的就是那颗 emoji） | ✅ 是 |
| 有歪才 append | 11 | 3 种（有歪+emoji / 没歪无 lost / 有歪无 emoji） | ❌ 否 |

用户要的是「25 行格子对得齐」，**有歪和没歪必须是同一种 DOM 结构**，
所以必须留占位——别为省事改成条件创建。

代价是空 span 宽 0 **却仍是 flex item**，前后各吃一个 `gap: 6px`，于是没歪的行
「emoji 到最后一个有文字的兄弟」变成 6 + 6 = **12px**，有歪的行只有 **6px**，
实测 14 个标记里 8 个没歪的比 6 个有歪的右移整整一格。
修法是纯 CSS 退掉那格：`.detail-char-lost:empty + .detail-char-luck { margin-left: -6px; }`。

**空占位与 `-6px` 是成对约束**：删任一个，没歪的 8 行 emoji 就会右移一格。
实测（四档全量，当前写法）：间距集合 = **`[6]`**（单值）、`marginLeft` 有歪 `0px` / 没歪 `-6px`，
空 lost 宽度恒 `0`。CSSOM 里相关规则共三条：
`.detail-char-lost { color: … }`、`.detail-char-lost[data-luck^="euro"] { color: … }`、
`.detail-char-lost:empty + .detail-char-luck { margin-left: -6px }`。

**量间距的正确口径**：要量到「emoji 前**最后一个有文字的**兄弟」。
直接量「emoji 到前一个兄弟」在没歪的行会恒得 `0`——空 span 宽 0，它的 right 就是它自己，
那是测量假象、不是布局。

## 颜色：算欧的不加红

用户原话「如果是算欧的，就不要加红色」。

档位键本来就挂在 `data-luck` 上（emoji 那颗用同一个属性），一处数据两处用，不会漂移。

### 右栏每行的欧 / 非标记（🌟 / 💀，按总抽倍率分 6 档）

用户原话（第一版）：「2 影 194 抽 歪 1 次 这个需要醒目一点，能看到这一角色是欧了还是非了，
在它背后加不同的 emoji？」**改前没有这个标记**，一行只有「N 影 / N 抽 / 歪 N 次」；
改后 UP 角色在 stats 行**末尾**多出 1~3 个 emoji。

位置口径后来变过一次：emoji 先是在行尾「紧跟『歪 N 次』（没歪时紧跟『N 抽』）」之后，
后来「歪 N 次」整体挪进 tip（见上一节），所以**现在 emoji 一律紧跟「N 抽」**。

用户原话（第二版，换判定口径）：「我要看的是这个角色总共的非欧度，按总抽数来看欧度吧？」
于是**判定从「每 UP 均抽」改成「总抽倍率」，从二分欧/非改成 6 档粗细**。
位置没动（仍是行尾），改的是「判多重」。下面「判定口径」一节写的就是这套新的。

位置经过两轮调整，**当前口径是行尾**：第一版放在行首（「N 影」之前）想做成一条可扫的竖列，
用户最终否掉了，原话「放在后面，不要放前面」。所以现在 emoji 是 `.detail-char-stats` 的
**最后一个子元素**，位置随每行文字长短而参差，**不排成竖列**。
**不许为了「对齐好看」把它挪回行首，也不许用 `margin-left: auto` 推到行最右**——
用户要的就是「紧跟文字后面」。

**「空占位多撑一格 gap」的补偿仍然生效**（`-6px` 在，别删）：
`detail-char-lost` 对没歪的角色是空 span 但保留占位，宽度为 0 **却仍是 flex item**，
前后各吃一个 `gap: 6px`，于是没歪的行「emoji 到最后一个有文字的兄弟」变成
6 + 6 = **12px**，有「歪 N 次」的行只有 **6px**，14 个标记里 8 个没歪的会比 6 个有歪的右移一格。
修法是纯 CSS 退掉那格：`.detail-char-lost:empty + .detail-char-luck { margin-left: -6px; }`
（`-6px` 与 `gap` 同值，**改 `gap` 时这里要一起改**）。

实测（四档全量、当前写法）：间距集合 = **`[6]`** 单值、`marginLeft` 有歪 `0px` / 没歪 `-6px`。
**它与空占位是成对的**，详见前面「为什么要留占位」一节。

**判定口径（用户选定，不要改）：总抽倍率分 6 档。**

> **改前 vs 改后**：第一版是「`每 UP 均抽 = pulls / upRounds` 对比理论期望 93.75 ±15%」，
> 二分 `欧 / 平 / 非`、一个 emoji。**这套已作废，不许和现在这套并存。**
> 现在是「`倍率 = 实抽 ÷ 期望抽数`」，6 档、可连排 1~3 个 emoji。

| 量 | 定义 |
|---|---|
| 期望抽数 | `upRounds × luckExpectPerUp`（`luckExpectPerUp` = 93.75 = `sPityExpect` 62.5 × `fiftyFifty` 1.5） |
| 倍率 `ratio` | `pulls ÷ 期望抽数` |

| 档位键 | 倍率区间 | 标记 | 中文名（进 aria-label） |
|---|---|---|---|
| `euro3` | `ratio < 0.35` | 🌟🌟🌟 | 极欧 |
| `euro2` | `0.35 ≤ ratio < 0.60` | 🌟🌟 | 很欧 |
| `euro1` | `0.60 ≤ ratio < 0.85` | 🌟 | 偏欧 |
| — | `0.85 ≤ ratio ≤ 1.15` | **不标**（不 append 任何节点，不是空 span） | — |
| `bad1` | `1.15 < ratio ≤ 1.45` | 💀 | 偏非 |
| `bad2` | `1.45 < ratio ≤ 1.80` | 💀💀 | 很非 |
| `bad3` | `ratio > 1.80` | 💀💀💀 | 极非 |

区间写进的 `config/report.json` 的 `numbers.luckTiers`（每档带 `emoji` / `count` / `label`），
期望基准写进 `numbers.luckExpectPerUp`，**都不硬编码在 charts.js**。
判定算在构建期（`build-report.mjs` 的 `luckOf()`），结果作为档位键（`'euro3' … 'bad3' | null`）
挂进 `report.charSummary`；渲染层只按这个键去 `luckTiers` 取 emoji / 颗数 / 中文名，
**不在前端重算**——两处各算一遍必然漂移。

**为什么按总抽而不按每 UP 均抽（用户选定这套的理由）**：19 只里有 **14 只只抽过 1 只**，
用「均抽」等于把单次运气当成角色属性。按总抽算，多只角色有对应的 `N × 93.75` 基准，
单抽一只的角色期望就是 93.75，判的是「这么快就出了」还是「抽了多久」。

**为什么用理论期望，不用账号均值**：账号均值会被整体运气拉平，同一只角色在不同账号会得到不同标记，
「欧/非」就失去了跨账号可比性。**也不是「歪没歪」**：
蕾米埃尔抽 3 只花了 194 抽、期望 281.25、倍率 **0.690 属欧**——194 这个绝对数看着吓人，
但 3 只的基准本来就是 281 抽（旧口径「均 64.7」结论相同，但那个数容易让人误读）；
简 159 抽只 1 只、期望 93.75、倍率 **1.696 才是很非**。抽数绝对值大不等于非。

**只对 `isUp === true` 判**。6 只非 UP（珂蕾妲 /「11号」/ 猫又 / 莱卡恩 / 丽娜 / 格莉丝）没有抽数据
（它们是被歪出来的，抽数记在别人头上），给它们判会算出 0 抽 = 极欧，纯属胡说。**不标也不占位。**

> 内高上限随内部滚动一起去掉了（见 §6「详情区不定高」），

**多颗 emoji 必须排在同一个 `span` 的一个文本节点里**，**不能拆成 N 个 span**：
`.detail-char-stats` 是 `display: flex; gap: 6px`，拆开的话每颗各吃一个 6px gap，

**无障碍**：emoji 是内容不是装饰，带 `role="img"` + `aria-label`，
取值是档位中文名（**极欧 / 很欧 / 偏欧 / 偏非 / 很非 / 极非**），不是「欧」/「非」两个字——
改了档位名之后 aria-label 也要跟着细，不然读屏只能读出粗粒度的方向。

**emoji 选型：🌟 欧 / 💀 非**（用户定的，中途从「四叶草」那版字符（U+1F340）换到 🌟，别再改回去）。
两个都是彩色 emoji，**没有一个偏暗**——先前有一段文档说「非」偏暗、对比度只有 2.05:1，
那是还在用「月亮脸」那版字符（U+1F31A，深蓝灰脸盘）时的测量，字符换成 💀 之后那段结论**已经作废**，

**不要用 CSS `filter` / `text-shadow` / `drop-shadow` 去「提亮」emoji**：那会让彩色 emoji
变形、且与系统字形不一致。要换只能换字符本身，不能靠 CSS 补救。
**不要加原生 `title`**：整行已有 `row.dataset.tip` 的自定义提示，两个会叠成两个 tooltip。

**构建期有断言**（任一不过 exit 1 且不写产物）：

| # | 断言 | 拦的是什么 |
|---|---|---|
| ① | 只许 UP 角色有标记 | 非 UP 没有抽数，标了就是 0 抽 = 极欧的胡说 |
| ② | 逐行用 `pulls / (upRounds × luckExpectPerUp)` **独立复算倍率并重新落档**，必须与 `luck` 一致 | 判定用错字段（比如还在拿 `pulls / upRounds` 比阈值，那是已作废的旧口径） |
| ③a | `luckExpectPerUp` 必须是正数 | 改成 0 或负数会算出无效倍率 |
| ③b | 每档必须有 `emoji` / 正整数 `count` / 非空 `label` | 渲染层直接取这三样，缺了就是空标记或空 aria-label |
| ③c | 档位区间不许重叠（`min` 小于上一档 `max` 就报错） | 上界写反会静默让一整档角色消失 |

③c **允许区间留空隙**——`0.85 ~ 1.15` 那段就是刻意留空的平档，「不标」正是要的效果。
第一版断言写成「相邻档必须首尾相接」，直接把这份合法配置判成了致命错误（实测报
`numbers.luckTiers.bad1.min(1.15) 与上一档的上界(0.85)不衔接`、exit 1）。
所以现在只拦**重叠**，不要求相接。

顺带一条教训：**构建期断言要真的跑一遍**。上面那次是断言本身写错、把正确的配置拦下来了，
反过来也会发生——断言漏了某条路径，坏配置就静默生成一屏看不见的标记。
每改一次档位表，先在有数据的情况下构建一次看它是不是**绿**的，而不是只看它「没有报错」。

### 右栏 tip：每次获得一行（紧凑格式）

用户原话：「Tip 不要太啰嗦」，并给了样例。实测雅展开**四行**（末行均抽是后来加的）：

```
本体：152 抽（77 抽歪「珂蕾妲」） · v1.4 · 2024-12-18
影画1：154 抽（77 抽歪「丽娜」） · v1.4 · 2025-01-03
影画2：78 抽 · v2.1 · 2025-07-16
均抽：128.0 抽（3 只 / 384 抽） · 歪 2 次
```

| 规则 | 说明 |
|---|---|
| 标签 | 第一只叫 **`本体`**，之后 `影画1`、`影画2`……（影画 N 对应第 N+1 只） |
| 结构 | `标签：抽数（歪出明细） · v版本 · YYYY-MM-DD` |
| 歪出明细 | `77 抽歪「珂蕾妲」`，角色名用「」；多条用顿号并列，**不拆行** |
| 直出 | **整个括号省略**，不写「直出」「没歪」——用户明确嫌啰嗦 |
| 分隔符 | ` · `（空格 + 中点 + 空格），数字与单位之间有空格 |
| **末行均抽** | `均抽：64.7 抽（3 只 / 194 抽） · 歪 1 次`——**永远在最后**，不插在明细中间 |
| 均抽口径 | `pulls / upRounds`，**保留 1 位小数**（`toFixed(1)`）；括号里是「`upRounds` 只 / `pulls` 抽」 |
| 均抽的歪 | 有歪才写 ` · 歪 N 次`，**没歪整节省略**（不写「歪 0 次」，同「直出不写括号」） |
| 均抽的标点 | 全角冒号「：」、全角括号（），` / ` 前后各一个空格，` · ` 连接歪 |
| 禁止 | 不要**别的**汇总行：「全部频段合计出现 N 次」「一共 N 抽」「追它共 N 轮…」 |
| 日期 | `recordTime` 转本地时区的年月日，不要时分 |

数据在 `charSummary()` 的 `gains` 字段里（每次获得的 `recordTime / version / total / losses[]`），
按 `recordTime` 正序。`losses` **只收 `round.losts`**（轮内歪掉的金）。

**`round.side`（十连副金）不能收进来**（这条写错过一次）：`side` 在轮次模型里的含义是
**「下一轮的 50/50 已经被这一发吃掉了」**（`markGuaranteed` 的 `guar`），不是「这一轮歪了」。
实测 `fixtures/baseline` 的南宫羽：`losts` 空、`side` 有猫又（同秒 `sort` 差 1），
它自己的 `lostRounds = 0`；若把 side 写进这一行，tip 会出现「45 抽（1 抽歪「猫又」）」，
与末行均抽里「没有『歪 N 次』这一节」（= 歪 0 次）直接打脸。反过来维琳娜那一轮 `side` 空、`lostRounds = 1`
（它的歪来自上一轮猫又那发副金），tip 这一行没有歪是**对的**——那笔成本记在带出保底的那一发上。

所以两个「歪」的统计范围刻意不同，**这不是 bug**：

| | 口径 | 回答的问题 |
|---|---|---|
| 均抽行里的 `歪 N 次`（原行内） | `round.off > 0 \|\| round.guar` 的轮数 | 追它一共歪过几轮 |
| 每次获得的括号 | 该轮自己的 `round.losts` | 这一次花了多少抽、期间歪出了谁 |

`guar` 那种轮次（歪来自上一轮带出的保底）没有可点名的歪出记录，所以 tip 那一行不写括号——
硬要写就得重复计上一轮的成本。

**这个差异是设计，不是漏写**（实测只有维琳娜一例，baseline）：均抽行末尾写着「歪 1 次」、
而它那一条获得却是 `本体：52 抽 · v3.0 · 2026-06-17` 没有括号。原因是它那一轮的歪来自 **v2.7 南宫羽那发十连的副金猫又**
（同秒 `sort` 差 1），那发把维琳娜的打保底吃掉了，而维琳娜自己 52 抽是直出。
**别为了「让两处看起来一致」给它补括号**——那会凭空把上一轮的成本记到这一轮头上。
真想补，得改轮次模型把 `guar` 的来源链一起传下来，那是另一件事。

**自检**：每个 UP 角色 `Σgains[].total` 必须等于行内显示的 `pulls`
（实测 19/19 全等；均抽行的括号里那个总数用的也是同一个 `pulls`）。
这条已写进构建期断言（`build-report.mjs` 末尾的 gains 校验），不等就退 1、不写产物。

同一处还有第二条断言：**「tip 里写了歪出明细的获得次数」不许超过该角色的 `lostRounds`**
（这个数现在**行内和 tip 末行均抽两处都有**）。
它专门拦「把 `round.side` 混进 `losses`」这个错——`guar` 轮自身没有任何 `losts`，
一旦把 side 掺进来，这个不等式立刻被打破。实测注入 side 后构建立刻失败并点名：

```
✖ 右栏 南宫羽 有 1 次获得在 tip 里写了歪出明细，但它只有 0 轮歪：
  疑似把十连副金（round.side）混进了 losses——side 的语义是「下一轮的保底已被吃掉」，不是这一轮歪
```

**歪的语义踩坑（写错过一次）**：早先用「`has5050` 频道里 `is_up === false` 的记录条数」当歪次数，
结果非 UP 角色全被标成「歪 N 次」。正确做法是走已有的轮次模型（`buildRounds` / `markGuaranteed`，
与主图同一套），它本来就区分「这一轮歪了」（`off > 0` 或 `guar`）和「这个金是被歪出的」（`round.losts`）。

**维琳娜案例（验证轮次口径用的）**：`sort=2154 t=1781710257 维琳娜 is_up=true count=52`，
`off=1`（那一轮前面真有 1 条非 UP 金）→ `lostRounds = 1`。
南宫羽那一轮的十连副金猫又（`sort=2102`，与 `sort=2101` 南宫羽同秒、差 1）属于 v2.7 的池子，
**与维琳娜无关**——`losts` 在每个 UP 处清零，不跨池带到 v3.0。
实测 UP 组歪轮合计 **14**。

**为什么影画必须跨频段**（这条被写错过一次，别再改回去）：独家频段能歪出常驻角色，
同一个角色的重复获取会散在不同频道里，按频道分开算**必然少算**。实测 `fixtures/baseline`：

| 角色 | 分布 | 分频道各算 | 正确（全局） |
|---|---|---|---|
| 珂蕾妲 | 独家 4 + 常驻 2 | 3 影 + 1 影 | **5 影** |
| 猫又 | 独家 2 + 常驻 2 | 1 影 + 1 影 | **3 影** |

这个错很隐蔽：每个 tab 单独看都对，只有把同一角色在两个频道的记录加起来才能发现。

**只收角色**（`item_type === 'ItemType_Avatar'`）：音擎 / 邦布没有影画概念，不进右栏；
常驻里的角色照常计入。实测 baseline 全局 **25 个角色 / 47 条角色记录**（19 个 UP、6 个非 UP）。

- **合并模式不影响右栏**：那个勾选只改变左栏怎么分行，右栏是全局聚合，与它无关。
- 排序：**UP 角色在前、非 UP 在后**；两组各自按**最后获得时间倒序**（所有记录 `record_time` 的最大值），
  最后按 itemId 稳定排序。不按名字（中文名排序对读者没意义），也不按出现次数——
  那样「从没 UP 过但最近刚拿到」的珂蕾妲会压在最新的 UP 角色上面。
- **右栏底部那句口径小字已删除**（用户原话「角色汇总底部那句描述不要」）。
  改前是一行 `.detail-chars-note`，文案是 `copy.detailCharsNote`：
  「影画按全部频段合并计算；抽数为该角色各轮的总抽数（含期间歪出的）。「歪 N 次」＝追它时歪过几轮」，
  固定在右栏最底部、带一条 `border-top: 1px solid #26262e` 的上分隔线。
  改后 `.detail-chars-note` 的 DOM、CSS 规则、`copy.detailCharsNote` 与 `copy._detailCharsNote` 三处**一并删掉**，
  右栏只剩 `.detail-chars-body` 一个子元素。
  **删它换回了多少可见高度**（`.detail-chars-body` 实测高度，当时右栏外框定高 480）：
  1440 body **439 → 480**，小字占掉 **41px = 2 行文本**；1000 / 800 body **424 → 480**，
  占掉 **56px = 3 行文本**（栏更窄、折得更多）；720 因为窄屏有 `max-height: 8 × 34 = 272` 兜着，
  body 一直是 272，小字只是把右栏外框总高从 **298 压回 272**。

  > `.detail-chars-body` 高度恒为内容自然高度 **854**（25 × 34 + 4），
  > 「多出几行可见」这个说法随之失效——删那行小字现在的收益只是**少占 41~56px 的整页高度**。
  口径本身仍然有效（影画跨全部频段合并、UP 抽数是各轮 total 累加、非 UP 只显示影画），
  只是**不再写在界面上**：这些规则留在本文档、`core.js` 的 `charSummary()` 注释和构建期断言里。
  别再把它加回来，也别改成更短的版本——用户说的是「不要这句」，不是「精简它」。

**实现放在数据层**：`core.js` 的 `charSummary()` 算好，挂在报告**顶层 `report.charSummary`**
（不在 `details[ch].chars` 里——放频道下会诱使人以为它该跟着 tab 变），
`charts.js` 的 `renderDetailChars()` 只画。**不要在渲染层重新聚合**——
那会让「左栏和右栏对不上」变成两处口径各写一遍。

**构建期有防回归断言**（`build-report.mjs` 末尾，三条都 `fatal` 退出 1 且**不写产物**）：

1. **影画必须跨频段**：凡出现在多个频道的角色，`appearances` 必须大于它在任一单频道的出现次数。
   已实测有效——把 `charSummary` 临时改回只取独家频道，构建直接失败并点名：

3. **抽数必须闭合**：UP 角色 `pulls` 之和 == 独家 + 独家重映官方已抽数。

第 3 条是这次新加的，专门拦「只累加 UP 那条 `count`」这个坑：它的症状极隐蔽，
每个数字单看都像个合理值（雅 230 也不离谱），只有**加起来**才暴露。


**图标目录不能按频道一刀切**：音擎频段一个频道里同时有音擎（id 在 `items/`）和歪出来的角色

### 6.2 版式三条（用户看过效果后定的最终形态）

用户原话三条：「抽卡详情的分栏感觉太宽了」「抽卡详情 文字太靠边缘」「抽卡详情 的几个 Tab 还是放到跟它同行试试」。

#### ① 标题左边缘对齐列表内容

`抽卡详情` 原来 x=21（卡片左边缘 x=20，只差 1px，紧贴边框）。现在标题文字 **x = 35**，
等于左栏每行最左侧那个**竖括号**（`.detail-bracket`）的 x——不是头像的 x（77），
因为一行最左的元素是版本括号列，头像在它右边。

做法：`.detail-head-main` 加 `padding-left: 14px`（= `.detail-list` 自己的 padding），
标题与 tab / tools 整组一起内缩。**不能给 `.detail-head` 加左右 padding**：
那会让它的内容盒比 `.detail-body` 窄 28px，同一个 `--detail-cols` 被压成 1058/300，
右栏标题立刻左移 14px、和右栏内容错开（实测 ctitle 从 1119 掉到 1105，头像仍在 1135）。

右栏标题的 `padding-left` 是 **16px** = 右栏 `border-left` 1px + `.detail-chars-fill` 的 11px
+ `.detail-char` 行的 4px，正好等于右栏第一个头像的 x（实测 1135）。

#### ② 分栏太宽 → **页面铺满 + 单一 gutter + 轨道跟着伸缩**

实测根因**不是**「卡片撑满视口」，而是**左栏吃到了内容用不到的宽度**：
1440 下左栏 1086，但 41 行抽数条最右只到 629（轨道写死 `width: 553px`），
右边整整白掉 **429~443px**，两栏 1086:300 看着就散。

**先说清哪一版是错的。** 期间落过一版「整页限宽 1000 居中」（`--page-max` 路线），
现在**已废弃，不要再加回来**：

| 方案 | 做法 | 1440 卡片 | 1440 左栏 | 1920 左侧留白 | 结论 |
|---|---|---|---|---|---|
| A 原状 | 轨道写死 553 | 1400 | 1086 | 429 | 左栏内部空一大块 |
| B 左栏收窄 680 + 两栏居中 | 只改 `--detail-cols` | 1320 | 680 | — | 列表漂到中间，不像贴左边框 |
| C 卡片限宽 1280 | `max-width:1280` | 1280 | 966 | — | 只把空白从 429 降到 323，观感没变 |
| D 卡片限宽 1000 | `max-width:1000` + `margin:0 auto` | 1000 | 686 | **460** | 把「只有详情卡窄」换成「所有卡一起窄」，问题没解决 |
| **E 铺满 + gutter + 轨道 flex（采用）** | 见下 | **1400** | **1086** | **20** | 页面铺满，左栏自己把宽度用起来 |

D 之所以是错解：它没动「左栏内部用不满」这个根因，只是把整页一起缩窄。
1920 宽屏下整页只剩 1000，左右各空 460——用户抱怨的「两边空的」原封不动。
**E 才是正解**：轨道改成跟着左栏伸缩，左栏多宽轨道就多宽，页面因此可以放心铺满。

两处改动，缺一不可：

1. **`--page-gutter: 20px` 是唯一 gutter 真源**。首屏 `.screen` 用 `padding: 16px var(--page-gutter) 10px`，
   第二屏 `.detail-panel` 在 `.screen` 之外（吃不到那段 padding），用
   `width: calc(100% - var(--page-gutter) * 2)` + `margin: 0 auto` 外缩。
   **两种用法、同一个值**，所以两屏的边缘严格相等；改其中一个就必须改另一个。
2. **`.detail-track` 用 `flex: 1 1 0` + `min-width: 0`，删掉写死的 `width: 553px`**。
   它吃满头像右侧的全部剩余宽度。条宽仍是 `(轨道宽 − 34) × 抽数 / 本视图分母`，
   所以同一档内条长与抽数严格线性；跨宽度时整条基线等比变长，**条与条之间的相对比例不变**。
   `min-width: 0` 不能省：grid 子项默认 `min-width: auto`，满格条会把左栏顶出列宽。

|---|---|---|---|---|---|---|---|---|

八档均满足：**首屏 4 块与详情卡左边缘极差 0、右边缘极差 0**（全部落在 `x=20` 起，
`右 = 视口 − 20`）；**没有侧边留白**；41 条轨道全在且**逐个等宽**（每档唯一宽度只有一个值）；

它量的是**轨道右沿到 `.detail-list` 内容盒右沿**（列表容器扣掉自己的 padding 之后），

属于列表的内边距，**不是漏白**——它和左栏标题的 14px 内缩是同一个数，两边靠它对齐。

> 判据是「轨道右沿与列表内容盒对齐」，**不是「条的右端贴容器边」**。

> 1440 下最长的条（独家 merged 159 抽）离容器边还有 204.7px —— 那是抽数不够，
> 不是布局没铺满。把两者混为一谈会得出「2400 还空 377 没修好」的错误结论。
> **分母是什么、为什么不再是写死的 100，见 §6.4。**
（`#detail-meta` 已删，这一行最宽的一块从 tools 组 220.5 降到 87 —— 见 ③。）

**限宽那一版留下的两个坑，若哪天又要限宽得记着**（当前不用）：
只写 `max-width` 而不写 `width`，块级元素 `width` 仍是 `auto`，卡片会贴住视口左边
（实测 1000 宽视口 `card.x=0`），要配 `width: calc(100% - …)` 才等价于外边距。

#### ④ 「真实抽数」紧跟 tab，不贴右边缘

用户原话：「真实抽数在小屏幕上跟右边的线贴到一起了。这个选项是不是靠左边的 Tab 一点？」
所以方向是**紧跟 tab 后面**，不是「右边留点空隙」、也不是「保持靠右」。

**改前**：`.detail-tools { margin-left: auto }` 把整组推到最右，
**右边缘到左栏内容右缘（`.detail-list` 的 right）恒为 0px，每一档都一样**——
这就是「贴线」，不是某一档的偶发。790 时左边离最后一个 tab 只剩 18px，于是两边都挤。

**改后**：`margin-left: 8px`（唯一的改动，就这一个属性）。8px 不是凑的：
790 是这一行最紧的一档，8px 时左边距 14px、右余 4px，两边都不贴；改成 0 则左边只剩 6px，仍偏挤。

六档实测（`fixtures/baseline`，左距＝最后 tab 右缘 → tools 左缘，右余＝tools 右缘 → `.detail-list` right）：

| 视口 | margin-left | 左距 | 右余 | 同行（top 差） | head-main 高 | 一行？ |
|---|---|---|---|---|---|---|
| 790 | 8px | 14 | **4** | 4 | 29 | ✅ |
| 800 | 8px | 14 | **14** | 4 | 29 | ✅ |
| 900 | 8px | 22 | **98** | 4 | 29 | ✅ |
| 1000 | 8px | 22 | **198** | 4 | 29 | ✅ |
| 1440 | 8px | 22 | **578** | 4 | 29 | ✅ |

改前同口径（`auto`）：左距 18 / 28 / 120 / 220 / 600，**右余全部 0**，同行差 4，head-main 29。
改后左距反而**更小**（14 / 22 而不是 18 / 28）：因为开关现在紧跟在 tab 后面，
不再被推到最右，间距由 `margin-left` 决定而与剩余空间无关。

两档两行区间（721 / 760）改前改后都是两行，`headH 61 / mainH 46` 不变，只是开关从
「第二行最右」变成「第二行最左」：721 改前 tools x=382、改后 x=43；760 改前 x=421、改后 x=43
（两档左距差都是 339 / 378，因为它现在跟在 tab 组后面而不是被推到行尾）。
**没有比改前更糟**：仍然是两行（`mainH` 46 不变）、没折成三行，开关落在第二行行首
（x=43 = 左内边距 14 + `margin-left` 8 + 容器 x=21），没有溢出左栏左边界（x=21）。
注意它和标题不在同一视觉行（标题占第一行 x=35~95），所以「43 < 95」并不构成重叠——
判重叠要看同一行的纵坐标，不能只比横坐标。

**为什么不用 `auto`**：`auto` 吃满剩余空间，右边缘永远顶到内容右缘，间距恒 0——用户报的就是这个。
**为什么不用 `0`**：790 那一档左边只剩 6px（实测），比改前的 18px 还挤，等于把问题从右边换到左边。

> 判据是「右余 > 0 且与最后一个 tab 同行（top 差 < 12）」，不是「看着居中」。
> **不许加 `justify-content`** 或别的布局属性来「调匀」——用户要的是「紧跟 tab」这一个效果，
> 加第二个布局属性会让这一行同时受两套分配规则支配，各档表现不可预测。

**tab 组与配置区之间有一条竖向虚线**（用户原话「中间加个虚线啥的吧，好区分 tab 和 配置」）。
落在 `.detail-tabs` 自己的右边缘上：

```css
.detail-tabs  { padding-right: 5px; border-right: 1px dashed #3a3a45; }
.detail-tools { margin-left: 2px; }   /* 原来是 8px */
```

**关键在净占用与改前完全相等**：改前 `margin-left: 8px`；改后 5（padding-right）+ 1（border-right）
+ 2（margin-left）= **8px**。所以 790/800/900/1000/1440 五档的 `tools` 与 `label` 坐标
**逐个浮点数完全不变**（实测 `IDENTICAL`）。颜色 `#3a3a45` 与 `.detail-list` 分隔线、
`.detail-chars` 的 `border-left` 同一色阶。

> **不许把这条线画在 `.detail-tools` 上**（`border-left` + `padding-left`）。
> 那会真的多占宽度：790 那一档只有 18px 余量，实测挤成左 6 / 右 3；
> `margin-left: 0` 再加虚线则 790 直接折行。
> 画在 tab 组上、靠重分配原有的 8px 腾位置，才是零位移的做法。
> 也不许换成实线 / 更粗 / `border-image` / `outline` / 伪元素。

**721 / 760 两行档要单独说明**：这两档开关本来就在第二行，改后 x 从 43 变 **37**（左移 6px）。
不是线撑出来的——第二行的起点是 `.detail-head-main` 的内容盒左缘（x=35）加 `margin-left`，
所以 `margin-left` 从 8 改成 2，行首缩进就跟着减 6。两行结构没变（headH 61 / mainH 46），
也没折成三行。若要这两档保持 43，就得让 `margin-left` 在折行时仍是 8——那会打破净占用相等的约束，
五档位置就不再零变化，**取零位移为主，两行档接受这 6px**。

**标题同行的判据是基线对齐**：`.detail-head` 用 `align-items: baseline`，不是 center/start。
center 在 800 折行时会把右栏标题居到两行中线（比左栏低 9px）；start 在 1440 下差 4px；
baseline 两者同为 15px/700，两条都过（实测 y 差 0px）。

**左栏内容本身一行没动**：41 行逐行比对 `class / data-side / tip / 条文字 / 条宽 / 条底色 / 图标 / 整行文本`
八项，与改动前**不同 0 行**。

**⚠️ `.detail-bar` 类名不能用**：左栏每行的抽数条也叫 `.detail-bar`（`height:17px`、`flex:0 0 auto`）。
工具栏一度取名 `.detail-bar`，被这些规则压成 30px，800 下 tools 直接压到列表上
（实测 tools.bottom 1059 > list.y 1042）。改名前先 grep 类名。

**图标目录不能按频道一刀切**：音擎频段一个频道里同时有音擎（id 在 `items/`）和歪出来的角色
（id 在 `avatars/`），邦布全在 `items/`。所以走 `iconKeyFor()` 逐个 id **先试 avatars 再退回 items**。
按频道选一次目录会让其中一类整列掉到占位图上（实测一刀切 `items` 时 14118 / 14121 报缺失，那是两个角色）。

**响应式**：列定义写成 `.detail-panel` 上的变量 `--detail-cols` / `--detail-gap`，
`.detail-head`（两个栏标题）与 `.detail-body`（左栏列表 / 右栏汇总）**共用同一份**，断点只覆盖变量。
`minmax(0,1fr) minmax(220px,300px)`；≤1000 收到 `minmax(190px,240px)`（让右栏先缩，别把左栏挤扁）；
**≤720 才塌成一列**（721 起两列）。800 宽（用户的半屏窗口）必须仍是左右两栏。
**断点就是 720**，721 起两列、720 及以下一列。

> 曾一度抬到 760（理由：760 两列时左栏只剩 478、头部那一行需要 491，tools 必然折到第二行），
> 后来又退回 720：760 这一档折行只是一行变两行，而塌成一列会让 721~759 的并排直接消失，
> 用户的「>720 行为一个字都不能变」这条压过「头部别折行」。

这个断点被改错过两次，都是「为了让头部不折行」而往上乱抬：

| 试过的值 | 后果 | 为什么不行 |
|---|---|---|
| **799** | 721~799 全塌成一列 | 把「两列但折行」换成「根本没有并排」 |
| **760** | 721~759 全塌成一列 | 同上，只是范围小一点，已退回 |

用户的要求是「**>720 行为一个字都不能变**」，这条优先于「头部那一行别折行」。
控件折到第二行照样能点能读；塌成一列则是用户要的并排没了。

**实测（当前代码）**：720 及以下一列；721 起两列，其中 721~798 头部折成两行
（`.detail-head` 60 / `.detail-head-main` 45），**799 起一行**（44 / 29）。
折行那一档左栏 436、可用 422，而一行最少需要 491 —— 折行是唯一正确的排法，不是 bug。

### 6.4 详情条的条长：频道内相对比例，不是固定 /100

**改前**：`charts.js` 用 `numbers.detailBarDivisor = 100` 这个写死的固定参照：

```js
const pct = Math.max(0, Math.min(1, row.pulls / CFG.numbers.detailBarDivisor));
```

**超过 100 抽的全部被封顶成满宽**。1440 下独家频道切到「真实抽数」（merged）时，
27 行里 10 行的条宽**完全相同、都是 948.11px**（实测）：

| 行 | 抽数 | 改前条宽 |
|---|---|---|
| 蕾米埃尔 | 108 | 948.11px |
| 叶瞬光 | 156 | 948.11px |
| 仪玄 | 104 | 948.11px |
| 仪玄 | 153 | 948.11px |
| 耀嘉音 | 101 | 948.11px |
| 雅 | 154 | 948.11px |
| 雅 | 152 | 948.11px |
| 简 | 159 | 948.11px |
| 青衣 | 110 | 948.11px |

153 抽和 104 抽肉眼分不出来——而「谁最贵」正是这一栏要回答的问题。
（默认的单金视图 all 里该数据集最长只有 82 抽，所以这个毛病只在 merged 模式下露出来。）

**改后**：分母由 `build-report.mjs` 的 `detailBarDivisor()` 现算，写进产物的 `details[].divisor`：

```
divisor = max(该视图所有行的最大 pulls, 该频道 channels[].pityCap)
```

`charts.js` 只用不算（与 `luckOf` / `perGold` 同一条「口径只在构建期算一次」的约定）：

```js
const divisor = d.divisor?.[merged ? 'merged' : 'all'] || 1;
const pct = Math.max(0, Math.min(1, row.pulls / divisor));
```

**`pityCap` 兜底解决「单条频道必然满格」**：只取最大值时，1 行的频道分母就等于那一行自己 → 必然 100%。
独家重映正好是这种情况（1 行 76 抽），拿该频道 `pityCap = 90` 兜底后是 **84.4%**，不满格。

实测各频道分母（`fixtures/baseline`，四档宽度分母相同，因为它只与抽数有关）：

| 频道 | 最长行 | pityCap | all 分母 | merged 分母 | 最长条占轨道 |
|---|---|---|---|---|---|
| 独家 | 82（简） | 90 | **90** | **159**（merged 最长 159，简） | 91.1% / 100% |
| 音擎 | 74 | 80 | **80** | **137**（霰落星殿） | 92.5% / 100% |
| 常驻 | 80（莱卡恩） | 90 | **90** | **90**（无 5050，与 all 同一份） | 88.9% |
| 邦布 | 74（咔嚓仔） | 80 | **80** | **80**（同上） | 92.5% |
| 独家重映 | 76（琉音） | 90 | **90** | **90** | 84.4% |
| 音擎回响 | —（0 行，只有垫抽行） | 80 | **80** | **80** | — |

**注意所有分频道的分母都 ≥ pityCap**（独家 all 90 = pityCap、音擎 80 = pityCap、
音擎回响 80 = pityCap）：这份数据集的每个频道最长行都没超过保底上限，
所以下限兜底全都在起作用。merged 的两个例外（159 / 137）是「一轮里歪掉的抽数累加」
越过了保底上限，那是真实成本，照实画到满格。

**all 和 merged 各自定标、不共用分母**：两者同一时刻只显示一个，没有并排比较的场景；
共用会让「all 最长 82 抽」把 merged 的 159 抽压成半格。用户已明确说两者不必一致。

**为什么不跟主图同轴**（用户原话「详情条的比例不需要和上方主图保持一致，各自独立」）：
主图比较的是「每一轮成本」在**固定 Y 轴**（`numbers.axisPullsMax`）里的位置，那是跨账号可比的基准；
详情条比较的是「这个频道里谁最贵」，是**频道内的相对排序**。两处各自独立定标，
读者不会拿主图的柱高去比详情条的条长——它们连单位刻度都没画。

**`detailBarDivisor` 这个配置项已删除**，同时删掉了 `numbers._comment` 里关于它的那句说明。
不要留两套分母并存，也不要把旧键名留下「以备将来」：它和现在的算法是互相矛盾的两套语义。

**垫抽条 `.pity-bar` 不走这套分母。** 它复用 `.detail-bar` 的类名（样式同源），
但分母是**它自己的保底上限**（`pity.cap`，进度占比 = `pity.cur / pity.cap`），
语义是「离保底还差多少」而不是「在这个频道里排第几」。两者不共用，
**别把 `divisor` 套到垫抽条上**：垫抽 58/90 = 64.4% 是对的，套上频道分母就完全说不通了。

**条宽的下限是文字宽度**（`.detail-bar { min-width: max-content }`，见 §6.5）。

#### 构建期断言（4 条，任一条失败则构建退出 1、不写产物）

分母写错不会报错，只会静默把长条压成一样长——所以必须靠断言拦：

1. `detailBarMinPx` 是正数（否则条塌成 0 宽）。
2. **分母 ≥ 该视图最长行的 pulls**。小于它意味着有行超出 100%，前端 `Math.min(1, …)` 会把它
   悄悄截成满格。
3. **分母 ≥ 该频道 pityCap**。这是「单条记录的频道不许必然满格」那条口径的实现方式。
4. **同一视图里 pulls 不同的两行，比例必须不同**（比例值 `pct.toFixed(6)` 去重）。
   唯一允许的例外是两行都被 44px 保底钳制——那时比例不生效、长度相同是刻意的。

**反向验证过**：把 `detailBarDivisor()` 改回 `return 100;` 后构建立刻失败，
报出 4 个致命问题（独家 merged「分母 100 < 最长行 159 抽」+ 十条同宽、音擎 merged 同样两条），
且**没有写出产物**：

```
✖ 频道 独家频段 的 merged 视图分母 100 < 最长行 159 抽：超出的行会被截成满格，不同抽数画出同样长度
✖ 频道 独家频段 的 merged 视图有不同抽数却同条宽：蕾米埃尔 108抽、叶瞬光 156抽、…（都算成 108 抽 / 分母 100 的比例）
```

#### 四档实测：改后有多少「不同抽数却同条宽」

`fixtures/baseline`，四档 × 六频道 × 两个模式全量（`.detail-bar` 不含垫抽条）：

| 视口 | 独家 all | 独家 merged | 音擎 all | 音擎 merged | 常驻 | 邦布 | 独家重映 | 音擎回响 |
|---|---|---|---|---|---|---|---|---|
| 1440 | 1（保底） | **0** | 0 | **0** | 0 | 0 | 0 | 无行 |
| 1000 | 1（保底） | **0** | 0 | **0** | 0 | 0 | 0 | 无行 |
| 800 | 1（保底） | **0** | 0 | **0** | 0 | 1（保底） | 0 | 无行 |
| 720 | 1（保底） | **0** | 0 | **0** | 0 | 0 | 0 | 无行 |

剩下的「同宽」全部是 **44px 保底**造成的，且都出现在低抽数端（1 抽 / 3 抽 / 5 抽 / 8 抽），
例如 1440 独家 all 的「3抽」和「1抽」都是 44px。**这是保底的正常行为，不是分母算错**：
它们本来就被下限钳住，改前改后都一样。判据是「同一宽度上不同的抽数必须能区分，
除非两者都被保底钳制」。

> 别把「保底造成的同宽」当成 bug 去修。把 44px 抬到 48px 只会换来「5 抽和 8 抽仍然同宽」，
> 因为总会有更小的抽数落在下限上。**下限必须存在**，否则 1 抽画出来只有几个像素、
> 里面的「1抽」两个字根本放不下。

### 6.5 条里的文字不许被裁：`min-width: max-content`

**改前**：`.detail-bar` 的宽度是 `max(44px, (轨道−34) × pct)`，`overflow: hidden`。
那条 44px 保底只考虑「条别缩到看不见」，**没考虑条里的字放不放得下**。
短抽数的条正好卡在保底上，字就被切掉。

**实测 bug（800 宽，邦布频道）**：垫抽条 `.pity-bar` 的字是「已垫8抽」，**需要 48px**，
被 44px 卡住 → `scrollWidth 48 / clientWidth 44`，**溢出 4px，最后一个字被裁掉一截**。

| 视口 | 垫抽条文字 | 需要宽 | 改前实宽 | 溢出 |
|---|---|---|---|---|
| 1440 | 已垫8抽 | 95 | 94.8 | 0 |
| 1000 | 已垫8抽 | 57 | 56.8 | 0 |
| **800** | **已垫8抽** | **48** | **44** | **+4** ❌ |
| 720 | 已垫8抽 | 54 | 54 | 0 |

只有 800 这一档露出来，因为它的轨道宽 402.1、`(402.1−34) × 8/80 = 36.8px` 低于 44，
被保底钳住；1440 的轨道 982.1 算出来是 94.8px，远超保底，所以一直没暴露。

**改后**：`.detail-bar` 加一行 `min-width: max-content`。让内容自己把条撑到够宽：

| 视口 | 改前实宽 | 改后实宽 | 改后溢出 |
|---|---|---|---|
| 1440 | 94.8 | 94.8 | 0 |
| 1000 | 56.8 | 56.8 | 0 |
| **800** | **44** | **48.03** | **0** ✅ |
| 720 | 54 | 54 | 0 |

**只在「内容比 44px 还宽」时生效**：长条本来就更宽，不受影响——所以 1440 / 1000 / 720 三档
一个像素都没变，只有 800 那行从 44 变 48。

**不会把条挤出轨道、也不会占掉右侧歪章预留的 34px**，实测四档 × 六频道 × 两个模式全量：

- 条右沿 → 轨道右沿的最小余量是 **34.00px**（1440 独家 merged 的 159 抽，正好是预留值），
  **越界 0 次**（余量 < 0 的实例数 0）
- 条右沿 → 歪章左沿的最小余量 **≥ 0**，**压到歪章 0 次**

原因是量级差得远：条自身的 max-content 最长也就「已垫58抽」约 56px + 12px padding = 68px，
而最窄的轨道（800 宽）有 402px；那 34px 是公式里从轨道宽扣掉的**常量**，
与条自身宽度无关，所以条变宽不会去动它。

**`.pity-bar` 不需要单独处理**：它和 `.detail-bar` 是同一个类（`.detail-bar.pity-bar`），
`min-width` 继承同一条规则。别为它单写一份——两份必然漂移。

> 这类「保底宽 vs 内容宽」的冲突，正确做法是让**内容决定下限**（`max-content`），
> 不是把保底值往上调。调 44→48 只是把边界推到下一个更长的文字上
> （「已垫58抽」需要 68px），而且 800 那档本来不该被这么宽的下限影响。
> 实测确认过：`min-width: max-content` 后全频道 overflowPx 全部 ≤ 0（即 0）。

### 6.6 左栏 tip 的「本体 / 影画N」：必须全局编号

**改前**：左栏每一行 tip 的第一行只有光秃秃一个名字（`菲欧妮`），同一行内看不到「这是第几只」。
右栏有影画数，但它是**聚合**的（「2 影」），读者想知道「左栏这一条具体是第几只」时只能自己数。

**改后**：第一行变成 `名字 · 本体` / `名字 · 影画N`（用户原话：「菲欧妮・本体/影画一 ——
在 up 角色后面也加下这个」）：

| 情形 | 第一行 |
|---|---|
| 第 1 只 | `菲欧妮 · 本体` |
| 第 2 只 | `菲欧妮 · 影画1` |
| 第 3 只 | `菲欧妮 · 影画2` |
| 音擎 / 邦布 | `琳琅鎏心`（不加，见下） |

措辞用「本体」而不是「0 影」：游戏里没有「0 影」这个说法，第 1 只就叫本体。

#### 为什么必须全局编号，不能按频道各自从 1 数

影画是**账号级**属性，而同一个角色的重复获取会散在不同频道里。实测 `fixtures/baseline`：

- **珂蕾妲**：本体是「抽雅时歪出」（**独家**频道），影画 3 是「**常驻** 6 抽」
- 按频道各自数 → 常驻里那只珂蕾妲会显示「本体」，而右栏同一角色写「影画3」，**两栏正面矛盾**
- 全局编号 → 常驻那只显示「影画3」，与右栏一致

这不是理论风险，是**已经能被断言抓住的事实**：把编号改成按频道各数，构建直接失败：

```
✖ 左栏「本体/影画N」与右栏对不上 38 行：独家频段/all 珂蕾妲: 左栏「本体」≠ 右栏「影画5」
✖ 左栏最高影画编号与右栏 portraits 不一致 6 个角色：珂蕾妲: 左栏最高影画2，右栏 portraits=5
```

#### 编号来源：共用右栏那一份，不另写一套

构建期 `portraitIndex()` 直接拿 `charSummary()` 的 `gains`（UP 角色）/ `sources`（非 UP 角色）
建一张 `(itemId, recordTime, sort) → 第几只` 的索引表，再回贴到每一行：

- **三个字段都必须带**：同一角色同一天拿到两只时 `recordTime` 相同，
  只按时间匹配会把两只标成同一号（实测 `fixtures/multigold` 有多金同秒对）。
- **不在前端重算**：`charts.js` 只读 `row.portrait`。重算必然与右栏漂移，
  而漂移的症状（左栏说影画2、右栏说影画1）没人会主动去查。

#### 为什么音擎 / 邦布没有这个标记

- **音擎**重复获得是**精炼**（`ItemType_Weapon`），游戏里没有「音擎影画」这个概念
- **邦布**整列都是邦布，同样没有影画

给它们标「本体/影画」是术语错误。判据是**逐行的 `itemType`**，不是按频道一刀切——
常驻频段里角色和音擎**混排**（实测 `fixtures/multigold` 常驻 5 行角色 + 2 行音擎），
按频道判断会让那 2 行音擎也带上「本体」。`detailRows()` 的 `itemType` 直接照抄原始金记录的
`item_type`，音擎频段里歪出来的**角色**照样会被正确标记。

#### 构建期断言（3 条，全部 fatal）

| # | 断言 | 反例 |
|---|---|---|
| ① | 左栏每行 `portrait` == 右栏同 `itemId` 那条的编号 | 改成按频道各数 → 38 行失败 |
| ② | 左栏某 `itemId` 的最高编号 == 右栏该角色 `portraits` | 珂蕾妲 左栏最高影画2 vs 右栏 5 |
| ③ | 音擎 / 邦布行不许有标记 | 误按频道判断 → 常驻那 2 行音擎被标 |

② 是对 ① 的独立补刀：① 只证明「查表查到了」，② 证明「表里装的东西本身对」。

#### 实测（两份数据集全量）

| 数据集 | 左栏角色行（带标记） | 非角色行（被错标） | 最高影画 vs 右栏 portraits 不一致 | 页面上带标记的 tip 行 == 数据里 `portrait` 非空 |
|---|---|---|---|---|
| `fixtures/baseline`（绳匠A） | **80** | **0**（共 95 行） | **0** / 25 个角色 | 80 == **80** |
| `fixtures/multigold`（绳匠B） | **183** | **0**（共 113 行） | **0** / 24 个角色 | 183 == **183** |

抽数闭合不变：19 个 UP 角色合计仍 **2448**（2372 + 76），断言没动。

#### 第三行措辞：「距上一金」→「距上一个金」+ 首金单独一句

用户反馈「距上一金 这个词咋怪怪的，这不就是本轮的抽数么」。核实后发现**那个前提只在合并视图成立**，
于是用户拍板走「保含义、只把词改清楚」这条：**数字一个不动**，只改文字。

| | 改前 | 改后 |
|---|---|---|
| 默认视图 · 普通行 | `距上一金 76 抽 · UP` | **`距上一个金 76 抽 · UP`** |
| 默认视图 · 该频道首个金 | `距上一金 50 抽`（其实是错的） | **`本频道首个金，50 抽`** |
| 合并视图 | `本轮 159 抽 ＝ UP 82 + 歪 77` | **一个字都没动** |

「上一金」→「上一个金」只是读顺，含义不变。

#### 默认视图为什么不能写「本轮」

`row.pulls` 在默认视图取的是 `g.count`（这一金距**上一个金**的抽数），
**本轮 total 还要加上期间歪出的（`off`）和十连副金（`side`）**。实测 `fixtures/baseline`
的 36 个 UP 行里有 **17 行**两者不等：

| 行 | 默认视图显示（`g.count`） | 该轮真实 total |
|---|---|---|
| 简 | **82** | **159** |
| 叶瞬光 | **50** | **104** |
| 雅 | 75 | 152 |
| 仪玄 | 75 | 153 |
| 菲欧妮 | 3 | 24 |

把叶瞬光的 `50` 写成「本轮 50 抽」就是错的——它本轮其实抽了 104 抽。
`fixtures/multigold` 同口径：97 个 UP 行里 39 行不等。

合并视图用的本来就是 `r.total`，那里写「本轮」才准确，所以只改默认视图。

#### 「本频道首个金」的判据：是定义，不是 `count === sort`

判据：**该频道 all 视图里获得时间最早的那一行**（`recordTime` 最小，并列用 `sort` 最小兜底，
与 `charSummary()` 同一套排序规则）。构建期算好写成 `row.firstGold`，前端只读。

**为什么不用更省事的 `count === sort`**：那是现象，不是定义。`count` 恒等于「本行 sort − 上行 sort」，
首金那行的上一行是 0，所以现数据上它**必然**等于自己的 `sort`。但一旦 `sort` 重编号而 `count`
含了首金之前的垫抽，这个等式立刻失效：

| 构造场景 | 定义判据 | `count === sort` 判据 |
|---|---|---|
| sort 从 31 起（`count` = 31 = sort） | 金B ✅ | 金B ✅ |
| sort 从 1 起、但 `count` = 31（含垫抽） | 金B ✅ | **一个都找不到 ❌** |

第二种情况下整条 tip 会退回「距上一个金 31 抽」，而它前面根本没有上一个金。所以按定义判。

两份数据集上两种判据结果**完全一致**（9 个有金的频道逐个核对：绳匠A 猫又 50/50、格莉丝 17/17、
燃狱齿轮 68/68、左轮布 15/15、琉音 76/76；绳匠B 珂蕾妲 49/49、艾莲 79/79、深海访客 65/65、鲨牙布 72/72），
说明现数据没有那种边界，但判据按定义写才安全。

#### 一列模式：「代理人汇总」必须贴着它管的右栏

两列时「代理人汇总」在 `.detail-head` 里、右栏在 `.detail-body` 里，但两者**同属一个 grid 的同两列**，
所以标题天然就在右栏正上方。塌成一列后这个前提没了：头部整体排在前、右栏排在列表下方，
标题于是停在 tab 行下面、**左栏列表的上方**（改前实测 720 宽：标题 y=1413、右栏 y=1932，差 **519px**），
读起来像在给左栏起名。用户原话：「感觉是分层有问题，它不应该在抽卡详情里面」。

**解法是结构，不是绝对定位也不是 JS 搬 DOM**：≤720 时让 `.detail-panel` 自己变成一列 grid，
把 `.detail-head` / `.detail-body` / `.detail-main` 全部设成 `display: contents`，
它们的子项直接成为 `.detail-panel` 的 grid item，于是标题和右栏成了**兄弟**，中间只隔一个 `order`：

```
order 1  .detail-head-main   （抽卡详情 · tab · 真实抽数）
order 2  .detail-list        （左栏列表）
order 3  .detail-chars-title （代理人汇总）   ← 紧贴右栏正上方
order 4  .detail-chars       （右栏）
```

**标题的左内边距是 14，不是 38**：一列模式下两个栏标题竖着排，读者会拿它们互相比，
所以「代理人汇总」要跟**「抽卡详情」**对齐（用户原话：「角色汇总应该左对齐，类似抽卡详情」），
不是跟右栏角色名对齐。`21(卡片内沿) + 14 = 35`，与「抽卡详情」文字 x、每行最左竖括号 x 三者全等。
按角色名算（行 4 + 头像 26 + gap 8 = 38）会得 x=59，差 24px —— 那是和错误的对象对齐。
角色行自己的缩进不动。两列模式仍是 16（那里对齐的确实是右栏第一个头像，800 都是 555）。

为什么不搬 DOM：`renderDetailChars()` 只跑一次、切 tab 不重建，resize 时搬回去必然漏一次。

为什么不能常开：`display: contents` 会丢掉容器的 `gap` / `padding`，那正是两列对齐赖以成立的东西。
**只在 ≤720 生效，>720 两列行为一个像素都不变**——用「同一份 CSS 把这一个媒体查询块整个删掉」构建对照产物，
对 800/1000/1440/1920 四档、24 组测点（面板/头部/标题/两栏/列表/右栏/每行/轨道/条…）逐元素比对，
**Δ 全为 0**（`/tmp/yokai-eq.mjs`）。

还有个坑：`.detail-head` 变 `contents` 后它自己的 `padding: 9px 0 6px` 失效（不生成盒子），
那 9px 上边距要补到 `.detail-head-main` 上，否则标题贴着卡片上沿。

#### 一列模式：分隔线在标题**上方**，标题与「抽卡详情」同一条竖线

光调 `order` 还不够。第一版把分隔线留在 `.detail-chars` 自己身上（`border-top`），
而标题的 `order` 比它小、排在它上面，渲染出来是
「左栏列表 → 标题 → 横线 → 右栏列表」——**那根线把标题归到了上面那一块里**，
读起来就是「代理人汇总」还留在上一栏。用户第二次反馈原话：
「我指的是 角色汇总 那个标题的样式，还是在上一栏里面了，没有分离」。

正确顺序是「左栏列表 → 空白 → 横线 → 标题 → 右栏列表」：

| 做法 | 实现 | 为什么 |
|---|---|---|
| 线在标题上方 | `border-top` 挪到 `.detail-chars-title` 自己身上；`.detail-chars` 显式 `border-top: 0` | 线是标题盒子的上边框，横贯整张卡；线在标题上方才等于「从这里开始是新一栏」 |
| 线只有一条 | `.detail-chars` 的 `border-top` / `border-left` / `padding-top` **全部写成 0** | 本文件里 `.detail-chars` 出现在两处（一列块里两条规则会合并计算），漏一处就是两条线叠着 |
| 标题上方留白 ≥20px | `.detail-chars-title { margin-top: 20px }` | 10px 时用户仍读成「还在上一栏」；20px 才明确「列表结束了」 |
| 标题与「抽卡详情」对齐 | `.detail-chars-title { padding-left: 14px }` | 一列模式下两个栏标题竖着排，读者会拿它们互相比，所以「代理人汇总」要跟**兄弟栏标题「抽卡详情」**对齐（文字都在 x=35），**不是**去对齐右栏角色名。中间那版写成 38（照着名字的 `行 padding 4 + 头像 26 + gap 8` 算的），量出标题文字 x=59、与「抽卡详情」差 24px，用户原话：「角色汇总应该左对齐，类似抽卡详情」。角色行自己的内缩不动 |

#### 右栏每一行：34px 整数、note 让位、名字不用 mono

四项都是实测出来的，不是审美调整：

**① 行高 44 → 34px。** 原来只有 `padding: 5px 4px`，高度由内容撑，实测 **44px**；
而同一个页面里左栏每行只有 26px，两栏密度差太远，1440 下内容 1100px、可视 439px → **16 行被切**。
改成写死的 `--detail-char-h: 34px`（图标 26 居中，名字 16 + stats 14 + 1 间距 = 31 ≤ 34），
1440 可视区从 9 行变 **12 行**，760 从 6 行变 **12 行**。**字号一个没动**（12px 名字 / 10.5px stats 是下限）。

**② note 不再压住最后一行。** 容器本来就不重叠（1440：body 底 1958、note 顶 1962），
但滚动到底时最后一行会贴到那条分隔线上。给 `.detail-chars-body` 加
`padding-bottom: var(--detail-char-h)`（**整行**，不是随手 6px——这一层滚动位置按内容算，
留非整数就只看到「大半行 + 一条缝」）。实测四档滚到底：最后一行 bottom → note top 恒为 **38px**，
最后一行完整可见（超出 body 底 −34，即完全在内）。

> 这条和 note 一起作废了：note 已删（见 §6.1），`padding-bottom` 也从整行 34px 降到 **4px**
> ——没有内部滚动，「滚动停点对得上行边界」这个理由就不存在了。见 §6「详情区不定高」。

**③ 一列模式的 `max-height` 必须是行高整数倍。** 原来写死 `320px`，320 ÷ 44 = **7.27**，
第 8 行被切 12px。行高改 34 后第一版把 `8 × 34 = 272` 挂在外层 `.detail-chars` / `.detail-chars-fill` 上，
**实测仍是 246px = 7×34 + 8** —— 因为 `.detail-chars` 自己的 `padding-top: 8px` 和 1px 上边框先吃掉 9px。
所以上限**只给真正滚动的 `.detail-chars-body`**，外层两个容器一律 `max-height: none`。
修完 720/760 实测可视 **272px = 8 整行、余 0.00px**。

> **这条已整条作废**：那个 `max-height` 已经删掉了。现在窄屏也是整页往下长（见 §6「详情区不定高」），
> 没有「可视区必须是行高整数倍」这回事。留着是为了记住当时为什么会写那个上限，
> **不是要你把它加回来**。

**④ 中文名字不能用 mono。** 「「席德」」看着像往里缩，但量下来所有名字文本左边缘都是同一个 x
（1440 = 1169、760 = 549、720 = 59，**极差 0.00**）——布局是对的，是字体回退的视觉错觉：
`var(--mono)` 首选 `"DM Mono"` 多数环境没有，回退 Menlo，`「」` 的占位宽度和汉字不是一个比例。
**`.detail-char-name` 改 `var(--sans)`**；数字部分（影 / 抽 / 歪，即 `.detail-char-stats` / `.detail-char-overcap`）
继续 mono 保持等宽对齐。字号不动。

> 左栏不用改：左栏每行只有头像 + 条 + 抽数，没有角色名（名字在 tip 里）。

数据面不变：**25 行 / 19 UP / 6 非 UP**、「歪」列留空 8 行（歪过的写、没歪的**根本不产生文本节点**）。

**右栏高度改由自己决定（改前：只由左栏决定）。**

改前：右栏的在流内容为空（真正的列表放进**绝对定位**的 `.detail-chars-fill`，`inset: 0`），
所以它不参与行高计算，行高 = 左栏写死的 480；`align-items: stretch` 再把这个高度给右栏，
内部 `.detail-chars-body`（`flex:1` + `overflow-y:auto`）自己滚。

改后：左栏不定高了（见 §6 那条），右栏必须**回到正常流**，否则没有高度来源。
`.detail-chars-fill` 改 `position: static`、`.detail-chars-body` 去掉 `flex: 1` / `overflow-y: auto`
和「8 × 34 = 272」那个上限。`.detail-body` 的 `align-items` **保持 `stretch`**。

**为什么是 `stretch`，不是 `start`**（`start` 那版已推翻）：

`.detail-chars` **没有背景色**，盒子被拉长**不产生任何可见空白**——拉长 377px 还是 4px，
用户看到的画面一模一样。右栏唯一看得见的东西是 `border-left` 那条 1px 竖线，
而**它的长度就等于盒子高度**。所以盒子高度不是「无所谓」，它直接决定那条线画到哪。

两版实测（1440 独家，左 41 行 / 右 25 行；`.detail-list` 底边都在 2250）：

| 写法 | `.detail-chars` 高 | 竖线画到 | 视觉结果 |
|---|---|---|---|
| `start`（被推翻） | 854 | **1873** | 竖线在「格莉丝」下方**断在半空**，下面 377px 没线，像内容没加载完 |
| **`stretch`（现在）** | **1231** | **2250** | 竖线通到底，与左栏底边齐平 |

1000 / 800 两档同口径：`start` 竖线止于 1873，`stretch` 止于 2250，都是与左栏齐平。

> **曾经的信条已作废**：「右栏最后一行到底边 > 一个行高（34px）就说明被拉长」。
> `stretch` 下那个距离是 **381px**，但它量的是**不可见的盒子高度**，不是用户看得见的东西；
> 用户能看见的只有那条线的长度，`stretch` 下才是对的。判据要跟可见产物挂钩。

两种写法下 `.detail-chars-body` 的**内容高都是 854**（25 × 34 + 4），一点没变——
变的只是外层盒子和那条线的长度。**不要用「内容高 854」去论证 `start` 更好。**

`padding-bottom` 从「整行 34px」降到 **4px**：原来那一整行是**为滚动服务的**
（保证任何滚动停点都对得上行边界），现在没有内部滚动，理由不存在了；
4px 只为别让最后一行贴到容器下沿（与左栏的 `padding-bottom: 4px` 同量级）。

试过两条都不行：①`align-items: stretch` + 右栏在流内容 + 左栏定高 → 右栏 25 行把行高撑到 1141；
②左栏加 `contain: size` → 左栏高度直接变 0（实测）。

**一列模式（≤720）那条 `start` 保留**：两栏上下排列、各占一整行，`align-items` 管的是交叉轴，

### 6.7 详情左栏的版本过滤（1.x / 2.x / 3.x）

**改前**：「抽卡详情」头部只有频段 tab 和「真实抽数」，想只看某个大版本的记录做不到——
左栏把该频段所有版本组一次铺满（独家 41 行、16 个组）。
**改后**：「真实抽数」右边多一排 `1.x / 2.x / 3.x`，形态**照抄主图那排**（同一套 `.chip` 与图标常量），
勾哪个就只显示对应大版本的行。

#### 三条硬口径

1. **只管左栏，右栏一行都不过滤。** 「代理人汇总」是跨全部频段的全局聚合，
   过滤它会让影画编号和抽数对不上（影画序是全局第几只，含被筛掉的那些）。
2. **不改任何数字**：`row.pulls`、`divisor`、条长、分组口径全不动。过滤只挑「显示哪些行」，
   所以筛完之后的条长与分母仍按原视图算，不会因为筛掉几组就重新定标。
3. **默认全选＝不过滤；全部取消＝回到全显示**（与主图 `visibleIndices()` 同一约定），
   空集合绝不画成空列表。

#### 两个过滤状态必须独立

主图那排只影响柱子，详情这排只影响左栏行，**各自一个 `Set`**（`chartState.majors` / `detailFilterState.majors`）。
共用会让「勾了 2.x 结果主图和详情一起变」——用户没要求这个联动，
而且两个控件分处两个面板，共用状态时在 A 处的操作会在 B 处产生看不见来源的变化。
实测：详情只勾 1.x 时，主图那排仍是 1/2/3 全勾，柱子一根没少。

#### 某档位在该频段没有数据也照画 chip

「音擎回响」一个版本都没有、「独家重映」只有 3.1，但 chip **不按频段动态增删**：
按频段增删会让切 tab 时这排宽度跳变，读者会以为点错了什么。与主图同策略。

#### 筛空时的文案是另一句话

`detailEmpty`（「这个频段还没有 S 级记录」）在筛空状态下是**假话**：
频段里明明有记录，只是被当前勾选筛掉了。所以新增 `copy.detailFilterEmpty`
（兜底「当前版本筛选下没有记录」），两句话说的是两件事，**不要合并成一个键**。
文案里不带数字——勾了哪几档、筛掉多少行，chip 和行本身已经说明，再报一遍是重复。
实测（绳匠A · 独家重映 · 只勾 1.x）：左栏 0 行 + 这句文案，右栏仍 25 行。

#### 垫抽行跟着它所属的组走

垫抽行（`buildPityRow`）挂在**筛前最新的那个版本组**（`rows[0].version`）里，
不是「筛后第一个组」。那一组被筛掉时它跟着不显示；
**不能因为筛掉了 3.x 就把它挂到 1.x 组里**——那等于把「最新版本的垫抽」伪装成「1.x 的垫抽」。

#### 折行：整组当一个整体，不在组内断

用户拍板 A：**同行优先，放不下才折第二行**。1440 / 1000 一行到底；
900 / 800 / 760 / 721 整组折到下一行、**左对齐**（x=35，与「抽卡详情」标题同一条左线）。

实现：`.detail-filter-group` 是 `.detail-head-main` 里 `flex: 0 0 auto` 的单个子项，
且**自身不 wrap**，所以它作为整体掉到下一行，chip 之间不会断开。
≤840 再加 `flex-basis: 100%`——这一档「真实抽数」会先被挤到第二行，
没有这条时过滤组会黏在它右边（实测 x=109），加了之后整组占满一行、从 35 起算。

### 改前 vs 改后

这段改了两轮，第二轮的**方向**与第一轮相反，两轮都必须读懂，否则很容易把已删的东西加回来。

| | 最初 | 第一轮（已废） | 现在 |
|---|---|---|---|
| 口径算法在哪 | `scripts/build-report.mjs`，和 `readFileSync` / `createHash` / `writeFileSync` 混在 2453 行里 | `assets/report/core.js` | `assets/report/core.js`（不变） |
| 产物里内嵌什么 | 算好的 `window.__REPORT__`（约 1015 KB） | 算好的 `window.__REPORT__` | **原始采集 JSON（约 45 KB）+ core 的转换版 + charts.js**，浏览器现算 |
| 有没有第二个入口 | 无 | 有：粘贴面板 `app.html` + `app.js` | **无**。产物自己内嵌数据、自己算，粘贴面板已删 |
| 口径有几份实现 | 一份 | 一份 | **一份**（产物里跑的是它的构建期转换版，同源） |

第一轮的出发点是「让纯前端页面也能算」，做法是另做一个粘贴 JSON 的静态页。
用户否掉了这个方向，原话：「我不要粘贴，还是之前 skill 那套流程，只是之前构建的时候直接生成最终的
html 了，会把对应的渲染都计算好。现在是生成 html，html 里面要么内嵌要么加载几个爬取好的 json，
然后纯 js 渲染出最终的报表」。

关键区别：**要变的不是「有没有前端入口」，而是「产物里内嵌的是结果还是原料」**。
skill 的调用方式、CLI 参数、日志、退出码全都没变，变的只是 `report.html` 的内部。

### 结构

```
assets/report/core.js                    computeReport({files, cfg, icons, generatedAt})
      ↑ import                                    │
scripts/build-report.mjs                          │ scripts/core-inline.mjs 构建期转换
Node 外壳：读盘 → sha1 内嵌图标 → 拼模板 → 校验 → 写 HTML
                                                  ↓
                                       产物里的第 ② 段脚本（经典同步）
```

删掉的东西（**不要加回来**）：`assets/report/app.html`、`app.js`、`config.json`、
`icons/manifest.json`、`scripts/build-icons-manifest.mjs`、`scripts/test-app-browser.mjs`。
`test-core-pure.mjs` 现在把「这些文件不存在」钉成断言。

### 产物的三段同步脚本

```html
<script type="application/json" id="zzz-stats-payload">原始采集 JSON</script>
<script>core（转换版）+ 引导 → window.__REPORT__</script>
<script>charts.js</script>
```

**必须是经典同步脚本，顺序不能动。** `charts.js` 是 IIFE，第一句就是
`const R = window.__REPORT__; if (!R) return;`。一旦第 ② 段变成 `<script type="module">`、
`await import()` 或 `fetch`，第 ③ 段会先执行、`__REPORT__` 还是 `undefined`，charts.js 静默 return ——
**页面一片空白、console 干净**。而 `screenshot.mjs` 只等 `DOMContentLoaded + setTimeout(0)`，
四套用例也都在这个时机读页面，异步化会让它们间歇性扑空，且极难定位。

`scripts/core-inline.mjs` 的转换规则（写死在一处，不要在别处再写一份）：

1. 顶层 `export function foo(` → `function foo(`。core.js 只有这一种 export 形式，
   多一种就当场抛错，不静默留下半份 ESM。
2. 整段包进 IIFE（`'use strict'`），不污染产物页面的全局作用域。
3. 末尾调 `computeReport(...)`，把结果挂到 `window.__REPORT__`。
4. 所有注入的 JSON（原始数据、配置、图标索引）都做 `</script` / `\u2028` / `\u2029` 转义。

**不要为了内嵌把 `core.js` 改成 UMD / CJS。** 那会破坏「Node 与浏览器跑同一份源码」这条性质，
而差异只在浏览器端显形。转换只发生在构建期。

构建期有三道闭环（都是 fatal，坏产物不落盘）：

- 模板里出现的每个 `/*__NAME__*/` 都必须被消费过；
- 填完之后产物里 `/*__…__*/` 残留必须为 0；
- 内嵌脚本里 `export ` / `import` / `await` 出现 0 次、`computeReport` 取得到、
  `window.__REPORT__ = out.report` 在、没有裸的 `</script`。

### 接口契约（`computeReport`）

| 入参 | 含义 |
|---|---|
| `files` | **文件名作键**的虚拟文件系统：`index.json` / `meta.json` / `cur_pool_stat_<id>.json` / `hist_pool_stat_<id>.json`。值可以是接口原始响应（带 `retcode`/`data`）或已解包的 `data`，`retcode !== 0` 抛错 |
| `cfg` | `config/report.json` 的解析结果，**由调用方读**，core 不碰文件系统 |
| `icons` | `{ encode(dir,id), resolveId(id) }`。core 只把 key 贴到 `avatarKey` / `iconKey`，值由调用方决定 |
| `generatedAt` | 可注入的时间戳，默认 `new Date().toISOString()`。两端逐字节比对靠它 |

返回 `{ report, notes, internals }`。`notes` 是原先打到 stdout 的非致命提示（标签去重等）；
`internals` 给外壳的 fatal 断言用（`channelReports` / `details` / `index` / `metrics` / `tags` / `charSummaryRows`）。

**fatal 校验不进 core**：那些断言的前提是「产物不可信 → 退出 1、不写文件」，而 core 现在也在
浏览器里跑，那里没有「退出 1」这个概念。判由外壳判，算在 core 算。

**图标两端完全一致**：Node 外壳与产物里的引导脚本用的是**同一套** sha1 → base64 dataURL
（同一份 `icons/` 目录、同一份 `iconIds` 表、同一份 `iconData`）。所以 `report.icons`
不是「允许有差异的字段」，而是必须逐字节相同 —— `test-report-browser.mjs` 就是这么断言的。

### 纯度的硬约束

`core.js` 里**不许出现** `node:` import、`process`、`Buffer`、`require(`、`__dirname`、`__filename`、
`import.meta`，以及裸的 `readFileSync` / `writeFileSync` / `existsSync` / `readdirSync` / `createHash`。

`scripts/test-core-pure.mjs`（47 项）先**剥掉注释再 grep** 这些词：
不剥注释的话，文件头那句「不许出现 `node:` import」会把自己的断言判红（实测过一次）。

`cssVarBlock` / `textSubs` / `escapeHtml` 已从 core **搬回构建期**（`scripts/template-tokens.mjs`）。
理由：它们唯一的调用方是 Node 外壳（产物是拼好的静态 HTML，浏览器既不写 `<style>` 也不做文案替换）。
留在 core 里的副作用是 token 字面量（`'/*__COPY_CHART_TITLE__*/'`）会随 core 源码内嵌进产物，
让「产物里不许残留 `/*__` 占位符」那条断言永远命中自己。

## 9. 实现要点（ECharts 与踩坑记录）

### 9.1 ECharts 用法

- **用 SVG renderer**，不是 canvas：报表要干净缩放、导出图片更清晰。
- **头像**：`scatter` + base64 内嵌的 `image://`（构建时从 `assets/report/icons/avatars/<id>.png` 读入去重），x 用 **0 基索引** `[i, y]`，
  `symbolOffset` 做垂直错位——每多一层头像往下挪一个 `ICON_STEP`。
- **柱顶写总抽数**：`scatter` + `symbolSize: 1` + 透明 `itemStyle`，只留 `label`。
  偏移量必须按该柱的头像层数**逐条算**，写死一个 `distance` 会被头像盖住。
- **柱内段内写字**：同一个 `scatter` 思路，或用 series 的 `label.position: 'inside'`。
- **矮柱不需要「最小高度兜底」，柱子本来就画得出来。**
  曾经因为「1 抽 / 5 抽的柱看不见」而加过一个 `barMinHeight` 兜底把矮柱抬到若干像素，
  **那是错误的诊断**：实测多金账号独家频道（左轴 180、绘图区 518px）逐根像素采样，
  3 抽 8px / 5 抽 14px / 1 抽 4px / 2 抽 5px，柱子颜色是完整的 `#3F7BFF`，一根不缺。
  「看不见」的真正原因是**扫错了行**——拿基线往上 77px 那条横线去扫，而 3 抽的柱只有 8px 高。
  - 兜底还有害：它把 1 抽抬成 1.42 抽去画，图上那根柱比真实的高，而 tip 仍报 1 抽，两处对不上。
  - 真实数据永远优先于「好看见」。矮就矮，它本来就是 1 抽。**不要再加回来。**
  - 判断某根柱有没有画出来，正确方法是直接从 `echarts` 取几何再采像素：
    `convertToPixel({xAxisIndex:0}, i)` 得柱心、`convertToPixel({yAxisIndex:0}, total)` 得柱顶，
    **加容器偏移**（`#chart` 的 `getBoundingClientRect().x`，实测 +21）才是页面坐标。
    拿图表内坐标去对截图坐标会得到「偏了」的假象——这个坑已经踩过四次。
- **已废弃的写法**：双 x 轴、`markLine` 画百分比上限。**不要加回来**。
- **标签联动高亮分两类**，按标签是不是「跟不歪率有关」区分。分类写在 `config/report.json`
  的标签规则里（`highlight: "line"` = A 类；缺省 = B 类），**不在 JS 里按 id 硬编码**——
  以后再加 A 类标签只改配置。

  | | A 类：`非酋翻身记` / `薛定谔的非酋` | B 类：多金 / 连段 / 似非实欧 / 欧气附体 等 |
  |---|---|---|
  | 语义 | 讲**整条累计曲线的形状** | 讲**具体哪几根柱** |
  | 有没有「命中柱」 | 没有 | 有 |
  | 柱状图 | **整片**压暗（`[[0, n-1]]`，不绕开任何柱位） | 压暗**补集**，命中的柱保持原亮度 |
  | 柱顶数字 / 头像 | 一并压暗（`opacity 0.3` / 换暗灰 `#5a5a62`） | 逐项：命中的亮，其余压暗 |
  | 不歪率折线 | **置顶 + 加粗提亮**，浮在所有系列之上 | 不参与，保持原样 |
  | 白描边 | **不画**（没有命中柱可指认） | 保留：负责「点名」 |

  ### B 类：压暗补集

  - 给**未命中**的柱盖半透明深色蒙层，让命中的柱靠亮度差跳出来。理由：命中的柱可能只有 1~4px 高
    （实测「雅 1 抽」4px、双金组里 2 抽 5px），叠淡色带圈住了也看不出是哪根；压暗周围则**不依赖柱高**。
  - **必须是补集，且要支持多段**：多金标签常常有好几组（多金账号的「十连双金 ×5」命中 4 根柱位 9/47/50/59），
    只取首尾两段会把中间 10~46 也留在亮区，反差就失效了。
    正确做法是按命中柱位切段：`[0,7] [10,45] [48,49] [51,58] [60,70]`。
  - **不能用 `markArea`**：它在类目轴上按整格铺、与柱心错开半格，
    实测传 `[23.5, 26.5]` 会渲染到 24.65~27.49，整段右移约 1.15 格。
    改用 `custom` + `api.coord([p,0])` 拿精确像素。
  - **透明度取 0.7**（`DIM_ALPHA`）。0.55 时命中/未命中的实测对照只有 **1.90:1**，
    用户反馈「反差不够」；0.7 提到 **3.63:1**（命中柱 `(69,135,255)` vs 压暗 `(33,51,94)`）。
    0.75 以上未命中的柱会压到接近底色，读者会以为那些轮次没有记录。0.7 是两者之间实测出来的点。
  - 蒙层色走配置 `colors.barDim`（`#16161a`，与 `--bg` 同族），**不用纯黑**——
    纯黑会把柱子压成死黑一片，像图坏了。

  ### B 类的另一半：命中区主动提亮

  只把补集压暗，命中区就只是「没被压暗」，在深色底上仍是一块普通背景——用户原话是
  「大底色有点灰」，他要的是命中那块**主动变成一块亮区**。所以 B 类是**双向**的：

  - 补集 → `tagHighlight` 压暗（`colors.barDim`，alpha 0.7）
  - 命中区间 → `tagHighlightLift` 提亮（`colors.barLift`，alpha 0.1）

  **提亮层必须 `z: 1`，低于柱子（2）。** 只抬背景，柱体色值一个像素都不动。
  早先的淡色带方案铺在柱子之上，把柱子和折线一起染白，看着像褪色——那是这个改动
  唯一要避开的坑。实测：命中区背景 `(29,29,35)` → `(59,56,57)`（明显变亮），
  而同区域柱体 `(63,123,255)` → `(69,135,255)`（只有 highlight 白边带来的提亮，
  **不是被染色**）。

  data 与压暗层互补但独立：压暗层拿补集，提亮层拿命中柱位自身，相邻命中柱要先合并成
  连续区间（`[24,25,26]` → `[[24,26]]`），否则中间会出一条条比柱还细的亮缝。
  两个函数（`setDimRuns` / `setLiftRuns`）都按系列名 `findIndex` 定位，不按下标。

  **A 类不铺提亮层**（它整片压暗、没有命中区），且 A 类 hover 时要显式 `setLiftRuns([])`
  清空——从 B 类标签直接划到 A 类标签不会先触发 `mouseleave`，不清会残留一块亮区。

  ### A 类：整片压暗 + 折线置顶

  - **折线置顶不能靠 z**。实测把折线 `z` 从 2.6 抬到 2.9、再加 `zlevel: 1`，
    蒙层照样压在折线上（28 个折线实心像素被按 alpha 0.7 合成：
    `(255,140,150)`→`(91,57,63)`，与 0.7 合成公式算出的 `(92,57,60)` 吻合）。
    可靠做法是**重建 option 并把 `winRate` 挪到 series 数组末尾**——最后绘制 = 盖在所有系列之上，
    同时把它的 `z` 设为 50、蒙层 `z` 设为 40，两条路一起走。
  - **提亮用的是「加粗本色」，不是白描边、也不是换亮色**。两种都试过并失败：
    ① 白色描边（0.55 白 / 5.6px）→ 线看着发白，三档红绿蓝糊成一片白，正是「一提亮就分不出好坏」；
    ② 换更亮的线色 → 绿蓝尚可，红档在深底上依然发闷。
    最终：折线本色线宽 1.4 → **2.2px**，描边保持原来的深色 4.6px，**色相一个像素都不动**。
    实测基线账号三档像素数 红 933 / 绿 635 / 蓝 205，全部可分辨；
    折线对压暗后背景的对比度 绿 4.24→8.21、蓝 5.78→6.73，靠背景变暗 + 线变粗产生「浮在最前」的感觉。
  - **`mouseleave` 必须整体复原**：`winRate` 被挪到数组末尾过，只关开关不会回到原层序，
    要用 `buildOption()` 重新 `setOption(notMerge)`。
    实测复原后与初始截图**整图逐像素 diff = 0**（不是抽样——抽样 6 万像素曾漏掉
    B 类复原未整体重建、头像残留变亮的 bug）。
  - 整片蒙层的 z 取 40（高于柱子 2 / 数字 3 / 头像 4，低于折线 50），
    这样「折线浮在最前、其余全部退后」是一条纯粹的层序关系。

  **复原必须走 `setOption(buildOption(), {notMerge:true})` 整体重建**，
  只清蒙层 + 把 opacity 改回 1 不够。原因：`dimLayers` 给数据项写进了**原本不存在**的
  `itemStyle.opacity` 字段，光设回 1 会让头像多出一层合成、看起来比原图更亮
  （实测 42707 个像素有差异、最大通道差 49，且方向是「复原后更亮」）；
  重建才能回到与初始渲染完全一致的字段状态。A 类一直有这句、B 类原先漏了，
  所以 B 类的复原 bug 靠抽样验收一直没暴露。

  ### 层序（下 → 上）

  ```
  提亮层 1 → 柱体 2 → 折线 2.6 → 蒙层 2.8 → 柱顶数字 3 → 头像 4
  ```

  按实际 z 值从小到大排。**B 类蒙层（2.8）压在折线（2.6）之上，这是用户定稿的要求**：
  非选中区的折线要被压暗（实测压暗区 1146 个折线像素、1138 个变化），
  命中区（补集洞里）不铺蒙层，因此那里的折线保持原色（45 个像素、0 变化）。
  不要看到「蒙层在折线上」就以为是层级写错了。

  折线仍**低于**柱顶数字与头像（用户定死的视觉口径：折线是辅助曲线，
  不能骑到「这一轮花了多少抽」「这一金是谁」上面）。

  **提亮层（z=1）低于柱子（2）**，只提亮命中区的背景、不染柱体颜色——
  这是「双向高亮」的另一半，见下面「命中区提亮」。

  A 类悬浮期间整体换一套：其余不动，折线提到 50 并挪到数组末尾、蒙层提到 40，
  即折线浮在所有系列之上。

  **多金青点已删除**（用户定的：那个小点没有信息增量）。多金信息现在只走两条路：
  柱上的标签文字、hover 标签时的高亮。

#### 多金标签的索引不能复用 `data-bars`

「十连双金 / 十连 3 金」也要能悬浮高亮对应柱，但它**不能**像连 UP / 连歪那样存 round 下标：

- `multiGold` 是**角色池 + 音擎合并**统计的（见 `multiGoldGoldsByChannel`），
  而主图一次只画一个频道，两边的 round 编号是**两套互不相干的编号**。
  把音擎那几组的 round 下标当角色池下标用，会高亮到完全无关的柱子上——而且不报错。
- 所以构建时只带**频道内 `sort` 序号**（`multiGoldSorts`），前端按当前频道现算柱位。
  当前频道里没有的那些 `findIndex` 返回 `-1`，自动跳过，切 tab 也不会错标。

前端换算只有 `barsOfTag()` 一个入口（多金青点已删，不再有两处共用的问题）：

```js
const barSortOf = (sort) => all.findIndex(
  (r) => r.sort === sort || r.side.some((s) => s.sort === sort),
);
```

`r.side` 那半句不能省：多金组的最后一金可能是「十连副金」，它不属于任何 round 的 `sort`，
只记录在某一轮的 `side[]` 里。少了这半句，副金落组的那些就找不到柱子。

早先青点与标签高亮两处各写一份映射时，曾漂成「青点在 A 柱、高亮圈住 B 柱」而两边都不报错。
**所以 sort → 柱位的映射只保留一个入口，不要在别处再写一份。**

实测（多金账号 71 柱）：

| 悬浮标签 | 独家频道命中 | 音擎频道命中 |
|---|---|---|
| `十连双金 ×5` | 6 根（4 组，柱位 8 / 9 / 46 / 47 / 50 / 59） | 1 根（1 组，另一金是副金） |
| `十连 3 金 ×2` | **3 根**（柱位 24 / 25 / 26，雅 79 → 1 → 5） | 2 根（柱位 13 / 14，另一金是副金） |

命中根数**少于组内金数**是正常的：同一发十连里排在 UP 之后的**副金**没有独立柱子，
它记录在某一轮的 `side[]` 里，只会随那一轮一起亮。所以「3 金组只亮 2 根」不代表漏画。

**一组多金的全部金都要亮，不能只亮最后一根。** 早先 `multiGoldSorts` 每组只存
`g[g.length - 1].sort`，于是一组三金只高亮 1 根柱子——标签写着「十连 3 金」，
图上只有一根亮，读起来像只出了 1 金。现在每组把**全部金的 sort** 都带上，
组与组之间用 `null` 占位分隔（展开成一维数组），前端逐组解析、逐根点亮。

`null` 分隔不能省：一组三金的三根柱必须一起亮，而两组双金不能因为挨着就串成一串。
前端遇到空段就知道「上一组结束」。

**音擎那组三金只有 2 根可亮**，因为第三金是同一发十连的副金，没有独立柱子
（它记录在某一轮的 `side[]` 里）。这是数据形状决定的，不是漏画。

基线账号的两组双金都在角色池（柱位 21 / 26），切到音擎 / 独家重映后命中 0 根——**不画高亮是正确的**，
不要为了「看起来有反应」而在没命中的频道里乱圈。

### 9.2 图标缓存

- 报表里不出现任何外链：`assets/report/icons/items/<item_id>.png`（64px 方形）与 `assets/report/icons/avatars/<role_id>.png`（64px 圆形）。
- **只有 64px 一套。** 96px 那套是中间产物（本身也是从更大的原图缩出来的），连同 `make-icons.mjs` 一起删掉了。
  依据：报表里图标最大显示 26 CSS px（详情行），主图柱顶头像 22px；DPR2 需要 52px，64px 够用。
  DPR3 下详情图标会略虚，这是确认接受的代价。
- 生成顺序：**先查缓存**，命中直接；缺的才下载，居中裁切后**直接裁成 64px** 写回缓存，一步到位、没有第二道压缩。
  头像在方形裁切后套圆形透明蒙版（`size*4` 画椭圆再 LANCZOS 缩到 64，避免边缘锯齿）。
- 下载失败用 `assets/report/icons/items/_fallback.png` 顶上，详情图标另加 `onerror` 回退。**不允许裂图，也不允许退回官方 CDN。**
- 本机 Python `urllib` 直连 CDN 常报 `CERTIFICATE_VERIFY_FAILED`，改用 `curl --retry 2`；
  darkmatter 单张约 7 秒，批量下载用 4–6 并发。

**`--preview` 和两档验收图是两个用途，不要混用。** 两档图（`1440x900` / `1280x800`，1x）
是**验收**用的：确认首屏装不装得下、图例有没有折行，看的是「这个尺寸下会不会破版」。
`--preview` 出的是**对外展示**用的 README 头图：1440 逻辑宽、DPR 2、**固定高度**。
当前实测 **`2880×2382`**（逻辑高 1191）。

#### `--preview` 按固定高度截，不是按内容过滤

用户原话（这是**第二次纠正**，第一次被理解错了）：

> 「README 的截图，抽卡详情那部分不要截太长，2 个版本够了」
> 「抽卡详情和代理人汇总都是按固定高度截图即可，**不是让你过滤抽卡详情**」

**改前两版都不对**，都记在这里，别再走回去：

| 版本 | 做法 | 问题 |
|---|---|---|
| 最早 | 整页 `scrollHeight` 截 | 详情列表铺满 **16 个版本组**（独家 41 行、v1.0~v3.3），图高 **4342px**，README 上一条细长条 |
| 上一版 | `--detail-versions N` **隐藏** `#detail-list` 下第 N 个之后的 `.detail-group` | **那是改内容**：图里只剩 2 组（6 行），右栏却还是完整的 25 行，两栏被强行修成不同深度。而且这个参数本身有坑（见下） |
| 现在 | **固定高度截图**（`clip` 到固定逻辑高），判据用**行盒** | 内容一个不少，截到高度就停；**两栏受同一高度约束**，谁超出谁被裁。名义 1200 → 实测吸附到 **1191** |

`--detail-versions` 参数、注入逻辑、两条默认值规则**全部删除**，不留两套机制让人猜用哪个。

**页面本身没改成定高滚动。** 用户早前明确要求「不要定高吧，抽卡详情多的话就直接在页面下面，
方便滚动截图」，所以这是**截图范围**的固定高度，`.detail-body` / `.detail-list` 的 CSS 一行没动。

#### 名义高度 1200 → 实际吸附到 1191（实测）

**硬切会在图末切出半行。** 左栏行高 26（含组间距 3px 会更杂）、右栏行高 34，
两栏行底边的**交集实测为空**（绳匠A 41 行对 25 行、共享底边 0 个）——不存在天然对齐两栏的高度。
（这一点与 §6.1 里「`stretch` 让两栏等高」不冲突：盒子等高，里面每一行的边界仍各走各的。）

**判据是行盒**（`getBoundingClientRect` 的整行），当前落盘实现就是这套。

> 曾有一版把判据改成「墨迹信封」（量文本 `Range.getClientRects()` + `img` + 有背景/边框的块），
> 并把这套说法写进了 AGENTS / README / SKILL / 本文档。那条实现**没有合进 master**，
> 只存在于分支 `backup/ink-envelope-176a153`（提交 `176a153`），`screenshot.mjs` 的 master 版里搜不到 `envelope`。
> 那一版实测 1192 / 图 `2880×2384` / 墨迹安全点 81，与行盒版的 1191 / `2880×2382` / 92 个**只差 1px，两版都是零半行**。
> 切换判据的顺序是：先 cherry-pick 实现、重出预览图，再改四份文档——反过来就会出现「文档描述了一个 master 上没有的实现」。
> **别在只改文档的情况下把数字写成墨迹那套。**

**为什么交集为空却仍有干净切点**：左栏相邻行之间有 **3px / 5px** 间隙
（41 行里 3px 25 处、5px 15 处），右栏间隙恒 0、步长恒 34，
所以「右栏某行底边恰好落进左栏行间空隙」的高度，两栏都不跨行，就是干净的。

这种高度**很稀疏**（视口 1440×900，只统计两栏都有行的区间）：

| 数据集 | 区间 | 干净整数高度 | 占比 | 1000–1400 内 |
|---|---|---|---|---|
| 绳匠A（`fixtures/baseline`，docH 2171） | 919–1769（851 px） | **6** 个 | 0.71% | **只有 1191** |
| 绳匠B（`fixtures/multigold`，docH 3979） | 919–1735（817 px） | **5** 个 | 0.61% | **只有 1055 / 1259** |

绳匠A 的 6 个干净点：`919, 953, 1191, 1429, 1463, 1667`
（按整页 1–2171 数会得到 1011 个，那是假象：其中 918 个落在详情区上方的空白里，那里根本没有行可切）。

所以必须**逐像素搜索**，不能靠公式算出一个「对齐两栏」的高度——那东西不存在。

脚本**上下两个方向逐像素校验**「没有任何左栏行 / 右栏行横跨它」，取离名义值最近的那个安全值
（只向下会出事：`--preview-height 1400` 一直掉到 1191，差 209px，用户会以为参数没生效；
实测离 1400 最近的安全值是 1429，只差 29px）。
在这个安全值之上再优先找**版本组底边**（组结束处最自然，图末不会像「组没结束」，
但只有它同样满足两栏不跨行时才采用）。
切口还必须落在详情区顶（`#detail-list` 的 `top`）以下，否则截出来的图整个详情区都没了。

绳匠A（`fixtures/baseline`）实测：

| 项 | 值 |
|---|---|
| 名义高度 | 1200 逻辑 px |
| **实际高度** | **1191**（吸附到名义高度下方最近空隙） |
| 图尺寸 | **2880×2382** |
| 左栏可见 | **9 行**，末行底 1189，**余量 2px** |
| 右栏可见 | **8 行**，末行底 1191，**余量 0px** |
| 完整版本组 | **4 个**（v3.3 2 行 / v3.1 4 行 / v3.0 1 行 / v2.7 2 行） |
| 被切半行 | **0** |

绳匠B（`fixtures/multigold`）实测：实际高度 **1259**、图 **2880×2518**、
左栏 11 行（末行底 1257，余 2px）、右栏 10 行（末行底 1259，余 0px）。

两栏余量不相等是正常的（一个 2px、一个 0px）——**只要都不是负数就说明没有半行**。

**实现错过一次，记下来**：当时取「左栏最近安全底边」和「右栏最近安全底边」的
**较小值**（1189），结果 1189 正好横跨右栏 1157~1191 那一行的中间。判据必须是
「这个像素两边都不切」，不能是「某一栏的底边」——后者只保证那一栏完整。

**内容比名义高度短时按整页收**（`Math.min(appliedHeight, docH)`），不会在底部截出一片空白。

#### 量几何必须按截图用的那个视口量（实测踩过）

行盒坐标全由排版决定，而**排版随视口高变化**：首屏 `.screen` 是 `calc(100vh - 26px)`，
同一份 `output/绳匠A/report.html` 整页高 **视口 1000 时 2271、视口 900 时 2171**，行边界整体位移。
`--preview` 的截图视口来自 `TARGETS`，是 **1440×900**。

用 1000 的坐标去判断 900 下的切点会算出**另一套安全点集合**（实测同一个 1191：视口 900 下两栏都不跨行，
视口 1000 下会同时切到左栏 1172~1198 与右栏 1189~1223 两行），于是把本来干净的 1191 判成不安全、
再顺着错位去找根本不存在的「对齐点」。而实际在 900 下 **1191 是干净的**（左栏 9 行末底 1189、
右栏 8 行末底 1191、4 个完整版本组、被切半行 0）。这个误判真实发生过一次，返工了一轮。

**注意别把这个误判记成「交集为空 ⇒ 没有安全切点」**：交集为空是真的，干净切点存在也是真的，
两者同时成立（干净点来自左栏行间隙）。1000 视口那次的错是**坐标用错了视口**，不是几何本身无解。

所以脚本在取几何**之前**显式断言 `window.innerHeight === TARGETS` 的 height，不等就中止；
收尾自检也把视口高记进 `written` 并一起比对（只比宽度不够：宽度对了、高度不对，
图会「尺寸看着对、切点却是按另一套排版算的」）。

#### 三条中止路径，都不许静默按名义值截

「找不到就不吸附、按名义值截」是**真实半行的来源**：它会安静地出一张切了半行的图，
而尺寸自检只比尺寸、永远是对的，拦不住它。所以下面三种情况一律 `failed += 1` + `continue`，
**不写文件**：

| 情况 | 触发条件 | 实测验证 |
|---|---|---|
| 拿不到页面几何 | `Runtime.evaluate` 失败 / JSON 解析不出 | — |
| **选择器量到空行盒** | `left.length === 0` 或 `right.length === 0` | 把 `detail-row` 改名后跑：`✗ 行盒选择器没量到内容（左 0 行 / 右 25 行），中止`，退出码 1，未写文件 |
| **上下都没有安全切口** | `down`/`up` 两轮扫描都没找到 `safeAt()` 为真的值 | 注入 `safeAt = () => false` 后跑：`✗ 名义高度 1200 上下都找不到「两栏都不跨行」的切口，中止`，退出码 1，未写文件 |

空行盒特别容易骗过人：`safeAt()` 对空数组恒真，于是**任何**高度都「安全」，
吸附看起来正常成功，切点却没人验证过——所以它必须和「拿不到几何」一样当成致命错误。

**拿不到页面几何时中止**（不写文件）：没有几何就无法保证不切半行，宁可不出图。

#### 旧实现（已删除）的两个坑，留着备查

`--detail-versions` 虽然删了，但它踩过的两个坑对任何「注入页面」的操作都成立：

1. **改 `.detail-group` 的显示状态必须同时写 `hidden` 和 `style.display`。**
   `.detail-group { display: flex }` 的优先级高于浏览器对 `[hidden]` 的默认 `display: none`，
   只设 `hidden` 的话元素照样显示、不报错，看起来像「参数没生效」。
2. **注入必须排在切 tab 之后。** 切 tab 会 `list.innerHTML = ''` 重画列表，提前改的会被冲掉。

**为什么必须由脚本出**：这张图以前是**手工截好随仓库带**的。结果是代码一路改（折线从黄变红绿蓝、
图例删了尾注、右轴从 60% 固定到 100%、加了版本过滤 chip），图一直停在初始化那一版，
README 上挂着一张和实际产物对不上的截图，而且没有任何东西会提醒你它过期了。

`--preview` 同时做**截图前断言**（不通过就中止、不写文件），方向按数据来源分两条

其余一律要求「**已**打码」（`eye=2` 且昵称/UID 都含 `*`）。
README 头图是对外公开的，这条断言比两档验收图更不能省——`--privacy` 参数传了不等于点中了。
真实数据那一支的行为与改前**完全一致**，一个字符都没放松。

- 脚本默认出 `1440x900` 与 `1280x800` 两张，核对**首屏无滚动、图例单行**。它复用 `drivers.mjs` 的 `findChrome()`，

**两个坐标轴必须固定：构建时自动断言，不达标会让构建失败。**

```bash
node skills/zzz-stats/scripts/build-report.mjs --data fixtures/baseline   # 坐标轴退化 → 退出码 1
```

校验分两级：

| 级别 | 行为 | 包含 |
|---|---|---|
| `fatal` | 打印 `✖`、**不写出产物、退出码 1** | 坐标轴退化：`charts.js` 没真正读 `CFG.numbers.axisWinRateMax` / `axisPullsMax`、配置缺失、某频道峰值超过固定上限 |
| `warn` | 打印 `⚠️`、照常出图、退出码 0 | 数据可疑点：缺图标（有占位图兜底，是设计好的降级）、金数/抽数口径对不上 |

坐标轴检查项：
- `config.numbers.axisWinRateMax` / `axisPullsMax` 是否配齐；
- **`charts.js` 里是否真的读了这个两个配置键**（先剥掉注释再匹配，否则会被解释这段历史的注释骗过去）；
- 每个可画频道的「不歪率峰值」是否超过右轴固定上限、「最高柱」是否超过左轴固定上限。

**为什么必须退出 1 而不是只打告警**：这条断言的整个存在意义是「不靠人记得」。
只 `console.warn` 然后 `process.exit(0)`，随手跑一次就漏过去了，下次照样静默退回自适应。
同理，**`writeFileSync` 必须在校验之后**——早先写在前头，就算退出 1，坏产物也已经躺在
`output/` 里了：CI 红了，但人打开文件看到的还是坏图。

验证方式（改这段代码后照做一次）：
1. 把 `charts.js` 里 `const winMax = CFG.numbers.axisWinRateMax` 临时改成 `(null)`（**注释保留**）；
2. 跑构建 → 必须退出码 1、打印「没有真正读取」、且**目标文件没有被写出**；
3. 改回来 → 退出码 0。

为什么要有这条：**右轴曾经「修好又退回去」一次**——左轴改成了「先读配置」，
右轴漏了同一步、只留了自适应，于是角色池显 60%、音擎显 80%，跨图没法对比。
之所以没被发现，是因为**独家重映那栏峰值恰好 100%、自适应出来也是 100%**，随便点开一个频道看着是对的。
**验坐标轴必须六个频道全验，不能只看一张图**：

| 频道 | 不歪率峰值 | 右轴应显示 |
|---|---|---|
| 基线账号 独家 | 50% | 100% |
| 基线账号 音擎 | 66.7% | 100% |
| 基线账号 独家重映 | 100% | 100%（这张恰好看不出问题） |
| 多金账号 独家 | 56.3% | 100% |
| 多金账号 音擎 | 100% | 100% |

**往产物里注入脚本时，只能插在最后一个 `</body>` 之前。**
报表把 ECharts 源码内联进了 HTML，那段源码的字符串里本身就含 `</body>`
（实测产物有 2 个匹配，第一个落在 echarts 内部）。用 `String.replace('</body>', …)`
会命中第一个，等于把注入脚本塞进 echarts 源码中间——表现为**图表整块变白**，
而且报错信息完全没有指向真正的原因。`scripts/screenshot.mjs` 的 `withPrivacy()`
就是用 `lastIndexOf('</body>')` 修的这个问题。

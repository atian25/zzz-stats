# 本地服务开发历史

以下从旧报表规范迁出，保留当时验收数字用于追溯，**不是当前接口或开发指令**。旧路径、导出、cfg/transport 参数及后来撤销的约束以本目录现行文档为准。

### 第四轮：本地 Web 服务 `scripts/serve.mjs`（2026-11-24）

前三轮都在命令行与产物内部。这一轮加一个**本地 Web 服务**，让用户能亲手在浏览器里走完
「扫码 → 取数 → 出报表」——命令行那条路要自己在终端里找二维码文件，体验不到这条链路。

| | 改前 | 改后 |
|---|---|---|
| 入口 | `collect.mjs` → `build-report.mjs`，两条命令 | 另有 `node scripts/serve.mjs`，浏览器里一条流程走完（两个 CLI 都保留） |
| 二维码怎么给 | 落 `output/login-qr.png`，靠图片服务 URL 给出去 | 直接 `<img src="data:image/png;base64,…">` 显示在页面上 |
| 进度 | 终端日志 | SSE 实时推到页面（申请二维码 / 已登录并查到角色 / 开始取数 / 采集完成 / 构建报表） |
| 取数路径 | 默认 node，失败降级 browser | **固定 node，服务里不降级**；失败把真实错误显示在页面上 |
| 重来 | 重跑命令 | 页面上的「重新出码」/「再来一次」，**不重启服务** |

设计上的几条硬约束（写进 `AGENTS.md` 与 `SKILL.md`）：

- **单文件、只用 `node:http`、前端 HTML 全内联、零 npm 依赖**。它是「让人亲手试一次」，
  不是产品化服务端：装依赖、拆静态目录都会带来安装步骤与版本漂移。
- **只调 SDK，不改 SDK。** 用现成的 `collectData({ transport:'node' })` / `buildReport({ files })`。
- **服务里不做降级**。降级策略仍然只在 `scripts/collect.mjs`（判据是「有没有显式传 `--transport`」）。
- **凭据不进日志、不进 SSE**：ticket / Cookie / set-cookie 一律不打印，页面上只出现二维码图片本身。
  代码里还有一层 `redact()` 兜底（已知 cookie 名、`ticket=`、`data:image/...;base64,` 都替换掉）。
- **落盘顺序与两个 CLI 一致**：先写 14 个原始响应到 `output/<账号名>/data/`，
  再构建；**校验通过之后才写 `report.html`**（与 `build-report.mjs` 同序，坏产物不落盘）。
- **改码要能杀掉旧的登录轮询**：`/api/start` 会先 `abort` 上一次运行。否则旧二维码继续轮询，
  万一有人扫了它，就会在后台静默登录成功并开始取数，用户完全不知道。

#### 这一轮抓到的真 bug：`JSON.stringify(Map)` 是 `{}`

`lib/build.mjs` 内嵌原始 JSON 时用的是**入参** `files`：

```js
.replace('/*__PAYLOAD_JSON__*/', () => escapeJsonForScript(JSON.stringify(files)))
```

而 `buildReport()` 的文档说「Map 与普通对象都收」，SDK 的 `collectData()` 返回的正是 Map。
`JSON.stringify(map)` **不报错、返回 `{}`** —— 于是：

- 构建日志一切正常、没有任何 `fatal`；
- Node 侧口径全对（`computeReport` 收到的是摊平后的 `fileMap`）；
- **只有打开产物才崩**：`statsOf()` 拿到 `null`，抛
  `Cannot read properties of null (reading 'type_stats')`，页面白屏。

CLI 一直传普通对象，所以这条路径从拆分那天起就没被走到过。是 `serve.mjs` 的浏览器验收
（真 chrome 打开 `/report`、收集 `Runtime.exceptionThrown`）抓到的。

修法一行：`JSON.stringify(fileMap)`。验法是**同一批 fixtures 分别用 Map 和普通对象构建**，
归一化 `generatedAt` 后两份 HTML 必须完全相同（实测 2,228,416 字符，逐字节相同）。

> 教训：SDK 声称「两种入参都收」时，**两条路都要有用例跑一遍**。
> 只测了对象那条，就等于只测了一半的承诺；而坏的那一半不会在构建期报错，
> 只在最终用户打开文件时显形。

### 第五轮：本地 Web 服务改成「多人同时用」（2026-11-24）

第四轮那版是按**单人**写的，用户要把它当多人同时访问的服务用，暴露了三个真问题。

#### 先说两条被撤销的约束

第四轮我给这个服务定了两条约束，用户明确撤销：

| 第四轮的约束 | 为什么撤销 | 现在 |
|---|---|---|
| 「HTML/CSS/JS 全内联进 `serve.mjs`」 | 错。仓库惯例就是拆到 `assets/` 下（见 `assets/report/template.html`、`assets/report/charts.css`） | `assets/serve/index.html` / `app.js` / `style.css`，`serve.mjs` 只管后端 |
| 「零 npm 依赖」 | 这条只对 **skill 本体**成立（要能被复制走）。本服务是本机开发服务，不需要守 | 按需引即可；这次仍然全用内置模块，但不再当硬约束 |

#### 三个必须修的问题

**① 首页要改成介绍页，不能自动出码。**

第四轮那版在 `DOMContentLoaded` 时 `fetch('/api/state')`，如果服务里还有一次运行就
**自动接上并直接显示二维码**。多人用时会直接串台：谁打开页面谁就看到别人的码。

现在：首次访问只有介绍页（标题 + 一两句说明 + 「开始扫码」按钮），背景是
`docs/preview.png` 那张报表预览（压暗 + 模糊，只做示例展示）。
**点按钮之后才实时申请二维码**；页面加载时不做任何网络请求，也不显示任何人的报表。
前端也不写 `localStorage` —— 刷新页面 = 重新开始。

**② 必须支持多人同时用。**

第四轮那版 `currentRun` 是全局单例，`startRun()` 里第一句就是 `cancelRun(currentRun)` ——
**第二个人点开始就把第一个人的扫码顶掉**，而且第一个人那边还在傻等一张已经作废的码。

现在：每次点「开始扫码」创建独立 run，各有各的二维码 / SSE 流 / 进度 / 报表。

```
POST /api/start                → { runId }        每次一个新的
GET  /api/events?runId=…       → 该 run 的事件流
GET  /api/state?runId=…        → 该 run 的状态
GET  /report?runId=…           → 该 run 的报表
```

- **所有按 run 取数据的接口都必须带 runId**，没有例外。
- **`/report` 不带 runId 返回 400，绝不猜「最近一个」** —— 猜了就是让 A 看到 B 的报表。
- 并发上限 `--max-runs`（默认 8）：满了 `/api/start` 返回 **503 + 明确文案**，
  **不踢掉别人的 run**（那正是第四轮那个 bug）。
- `RUNS` 只是 `id → run` 的查表，**不参与任何流程判断**，没有「当前 run」的概念。

**③ 报表和数据不落盘。**

第四轮那版 `writeEverything()` 往 `output/<账号名>/` 写 14 个数据文件 + `report.html`。
多人同时用时这会互相覆盖（昵称可能相同 → 同一个账号目录），而且这个服务的语义是
「当场看一次」，不是归档。

现在：`collectData()` 的 files 直接在内存里交给 `buildReport()`，HTML 存在该 run 上，
`/report?runId=` 从内存返回；run 结束 + 超过 `--ttl`（默认 30 分钟）后内存释放。
**要归档请用两个 CLI**，那套语义才是「一个账号一个目录、可以拷走部署」。

#### 这一轮抓到的真 bug：`meta.json` 不在 `files` 里

改成内存直通时我直接把 `collectData()` 返回的 `files` 交给了 `buildReport()`：

```js
const built = buildReport({ files: result.files, cfg: CFG, logWarn });
```

`collectData()` 的返回是 `{ uid, nickname, files, summary, meta }` ——
**`meta` 是单独一个字段，`files` 里只有 13 个键，没有 `meta.json`**
（`lib/collect.mjs` 文件头写着：「产出 14 个键的 Map（不含 meta.json —— 那个要昵称，由外层补）」）。

后果很安静：产物照样构建成功、`fatal` 是空的、报表也能打开，
**只是页面上昵称和 UID 全是空的**。CLI 那边是写盘时手动 `ordered.set('meta.json', meta)` 补的，
我重写成内存直通时漏了这一步。

是真浏览器验收抓到的：两个 run 各自跑完，`/report` 200、KPI 5 个、主图尺寸正常，
**但断言「甲的报表里有甲的昵称」红了**。补上 meta 之后 44/44 + 24/24 全绿。

> 教训：**「内存直通」不等于「把变量转手」**。落盘那一步除了写文件，
> 往往还顺手做了数据整形（补字段、定键序）；改成不落盘时，
> 这些整形必须显式搬到新路径上，否则丢的就是它们。

#### 验收（都是实跑数据，不是设计值）

| 验收项 | 结果 |
|---|---|
| 首页只有介绍页 | 无二维码、无上次报表、`document.body.innerText` 无「接上/上一次」 |
| 静态资源拆分 | `/assets/app.js`（`text/javascript`）、`/assets/style.css`（`text/css`）、`/assets/preview.png`（与 `docs/preview.png` 逐字节相同，681,185 字节） |
| 路径穿越 | `/assets/../lib/build.mjs` → 404，不含 `buildReport` 源码 |
| **两个独立浏览器上下文**（=普通窗口 + 无痕窗口）同时点开始 | 两个码内容不同、都 `naturalWidth=240`；各自跳到自己 `runId`；甲的报表含「浏览甲」不含「浏览乙」，反之亦然；两个主图 svg 都是 1238×591 |
| 按 runId 取报表 | 改成乙的 runId 拿到乙那份；不带 runId → 400；不存在的 runId → 友好 404，都不吐报表 |
| 并发上限 | 连起满 3 个都 200；第 4 个 503 且文案含「上限」；前面的 run 报表仍可取 |
| **`output/` 全程无新目录** | 前后都是 `绳匠A, 绳匠B` |
| console | 0 error |
| 七套用例 | 19 / 47 / 55 / 25 / 75 / 27 / 30 全过 |
| 假 passport 并发分流 | 44/44（含「A 的事件流里没有 B 的 uid」「A 的报表里没有 B 的昵称」） |

另外清掉了 `output/天猪/` —— 那是第四轮真人扫码跑出来的真实数据（UID 与每金记录）。
**`output/绳匠A`、`output/绳匠B` 保留**，它们是 `http://127.0.0.1:8899/...` 两个地址在服务的产物。

### 第六轮：服务前端三处体验修正（2026-11-24）

第五轮把服务做成多人可用的了，但**前端**还有三个体验问题。这一轮**只动
`assets/serve/` 三个文件**，`serve.mjs` 与 `lib/` 一行没碰。

#### ① 扫码之后要给二维码盖遮罩

用户原话：「扫码后那个二维码应该遮罩住，免得下面还在处理，上面还以为需要扫码」。

第五轮之后的行为：扫码确认 → 后端推 `已登录并查到角色` / `开始取数`，
**但二维码图片还亮在页面上**，倒计时还在跳，「换一张二维码」按钮还能点。
用户看着一张仍然清晰的码，会以为「是不是没扫上」。

现在：一旦进入扫码之后的阶段，二维码那一块立刻变换：

| 元素 | 扫码前 | 扫码后 |
|---|---|---|
| 二维码图 | 正常 | `blur(4px) brightness(.42) grayscale(.7)` + `opacity .55` |
| 遮罩 | 隐藏 | 覆盖在码上，写「已扫码，正在取数…」（`aria-live`） |
| 「换一张二维码」 | 可见 | 隐藏（码已失效，点了还会新起一个 run） |
| 倒计时 | 可见 | 隐藏（留着会让人以为还要再扫） |

**判据用后端实际推的阶段名，不靠计时器猜。** `app.js` 里 `PRESCAN_STAGES` 是白名单：

```js
var PRESCAN_STAGES = ['申请二维码', '二维码已生成，等待扫码'];
// 出现任何不在这两个里的阶段 → 当作扫码之后，盖上遮罩
```

白名单而不是黑名单：后端以后多推一个阶段名，黑名单会漏遮，白名单只会多遮一次——
遮着远比让用户重复扫要好。另外收到 `account`（拿到昵称/UID）也必然是扫码之后。
失败/取消时遮罩**留在原地但停掉转圈**（转圈的意思是「仍在处理」）。

遮罩只盖二维码那一块（`.qrwrap { position: relative }` + 遮罩 `inset: 0`），不是整页弹窗。

#### ② 介绍页示例图看不清、太小

| | 第五轮 | 现在 |
|---|---|---|
| 高度 | `min(52vh, 360px)` | `min(66vh, 520px)`（1440 视口实测 520px） |
| blur | `1.1px` | **去掉** |
| filter | `saturate(.85) blur(1.1px)` | `saturate(.92)` |
| 压暗 | 渐变盖到 `.72`（76% 处） | 前 58% 几乎不盖，最后 30% 才渐变成卡片底色 |
| 文字区位置 | `margin-top: min(34vh, 250px)` 压在图上 | **真实块高**：`.intro-hero` 撑开，文字区在它下方正常流式排布 |
| 深色模式 | `brightness(.55)`（只剩一团灰） | `brightness(.68)` |

**根因是定位方式，不是压暗参数。** 第五轮的 `.intro-inner` 靠 `margin-top` 压进图的下半段，
于是「为了让文字可读」只能把图压得越来越狠——两个目标互相打架。
改成真实块高之后，图的区域和文字的区域不再重叠，**图就不需要为文字让路了**。

#### ③ 整个页面/卡片太小

| | 第五轮 | 现在 |
|---|---|---|
| `.page` max-width | 720px | **960px**（1440 视口实测 960px） |
| 二维码 | 260px | **320px**（实测 320×320） |
| 卡片内边距 | 22px | 32px 34px 34px |
| 正文字号 | 15px | 16px |
| `h1` | `clamp(22px, 5vw, 28px)` | `clamp(26px, 4vw, 34px)` |
| 窄屏 ≤560px | 220px 码 | **220px 码**（保持不变） |

窄屏必须保持原样：这一轮一度把 `@media (max-width: 400px)` 也留成 200px，
结果 **390 的手机反而比旧版更小**。已删掉那一档——320 宽下
`320 − 14×2(页面) − 18×2(卡片) = 256 > 220`，放得下，不需要再缩。

#### 这一轮抓到的真 bug：`hidden` 属性没真的藏住

给遮罩加「藏掉换一张按钮」时，`app.js` 里写的是 `reissueBtn.hidden = true`。
**属性确实设上了、`btn.hidden` 读出来也是 `true`，但按钮仍然亮在屏幕上。**

原因：UA 的 `[hidden] { display: none }` 是**浏览器默认样式**，
而 `.btn { display: inline-block }` 是**作者样式** —— 作者样式永远胜过 UA 样式。
两个选择器特异度还一样（都是 0,1,0），所以是纯粹「层叠来源」的胜负。

我的验收断言写的是 `btn.hidden === true`，**全部通过**；
是截图里那个按钮还亮在二维码右侧才发现的。

修法：`style.css` 加全局 `[hidden] { display: none !important; }`，
断言改成测实际可见性（`getComputedStyle().display === 'none'` 且 `getBoundingClientRect().width === 0`）。

> 教训：**断言「藏起来了」要测渲染结果，不能测你刚设的那个属性**。
> 属性是你自己的意图，可见性才是用户看到的事实。同理，
> 前面几轮抓到的 `JSON.stringify(Map)`、`meta.json` 不在 `files` 里，都是同一类错误：
> 中间层「看起来成功了」，只有最终产物/像素是诚实的。

### 第七轮：14 寸笔记本上首页太高（2026-11-24）

第六轮把示例图放大到 520px，**在 14 寸笔记本上首页溢出了**。用户实测（真浏览器）：

| 视口 | 文档高 | 溢出 | 症状 |
|---|---|---|---|
| 1512×880 | 1031 | **151** | 按钮底边 877 贴着视口底，`.fineprint` 在 897~919 完全看不到 |
| 1512×820 | 1031 | **211** | 按钮直接不可见 |
| 1440×780 | 1026 | **246** | 同上 |

**根因**：`height: min(66vh, 520px)` 的 `520px` 硬上限。视口 820 时 66vh = 541，
取 520 —— 示例图独占 63% 屏高，加上文字区 399、页面内边距 112，总高必然 1031。

#### 解法：按「剩下多少空间」算，不按视口高度比例算

```css
--intro-budget: 450px;                                    /* 非图部分：页面内边距 + 文字区 + 余量 */
.intro-hero { height: clamp(220px, calc(100vh - var(--intro-budget)), 520px); }
```

为什么不是 `xxvh` 的比例：比例不认「文字区是固定高度」这件事。同一个比例在 820 高时算出 541（超），
在 780 时算出 515（还是超），而两者真正能给图的只有 370 / 330 —— 比例永远对不齐，只能靠 calc 减。

两个档位（互斥，不需要谁覆盖谁）：

| 档 | 条件 | 页面内边距 | 文字区内边距 | `--intro-budget` | 非图实占 |
|---|---|---|---|---|---|
| 收紧（默认） | 全部 | 24 / 28 | 24 / 28 | 450 | 52 + 375 = 427 |
| 宽裕 | `min-height: 1040px` | 40 / 72 | 36 / 40 | 520 | 112 + 399 = 511 |

**上限 520px 必须留着**：不留的话 2400 高的屏上图会撑到 1950px，把文字挤出首屏。
**下限 220px 也必须留着**：极端矮的视口（比如 1024×600）压到 220 就不再压，
允许滚动 —— 那时候优先保证图还能看出是报表。

#### 这一轮踩的两个坑

**① 媒体查询的位置比内容更重要。** 第一版把 `@media (max-height: 900px)` 写在了
`.intro-inner` 基础 `padding` 的**前面**。同特异度下后定义的规则胜出，于是：

- 示例图按公式缩到了 390（生效了）
- 文字区 padding 仍是 36/40（**没生效**，被后面的基础规则盖回去）
- 结果 1512×820 仍溢出 **21px**

**② 断点取整会让图出现「台阶」。** 宽裕档本来就该在 1031 启用（511 + 520 恰好装得下），
但那样 1030 那档算出 520、1031 那档算出 511 —— 窗口变高一点，图反而**缩了 9px**。
改成 1040 之后：1039 那档图是 520（已顶上限），1040 那档还是 520，接得上。
**判据是「示例图高度随视口单调不减」，不是「断点刚好落在临界值上」。**
